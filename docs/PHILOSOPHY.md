# C-lord の理念

> 迷ったときに立ち返る基準。機能や仕様の良し悪しは、コードや好みではなく、この理念に照らして決める。
> これは yousan の製品ビジョンであり、最終的に決めるのは yousan。
> 各機能が「どう動くべきか（あるべき動き）」は、この理念の下にぶら下がる。理念は「なぜ存在するか」、あるべき動きは「各機能がどう動くべきか」を担う。
> ただし、**この理念だけからは各機能のあるべき動きそのものは出てこない**。理念が決められるのは「誰があるべき動きを決めるか」「決まりがまだ無いとき何に照らして仮置きするか」まで。各機能の細かいあるべき動きは別途まとめる（#287 P1）。

---

## 核（一文）

**C-lord は、Claude Code ⇄ tmux ⇄ Discord をつなぐブリッジ。サーバーに常駐させた複数の Claude Code セッションを、文脈を保ったまま並行して進め、使い慣れた Discord からまとめて見渡し・判断・再開できるようにする。**

ここでいう「まとめて扱う」とは、たくさんの Claude Code セッションを、生の SSH+tmux を直接いじらずに、一覧して・判断して・続きから動かせる状態に保つこと。C-lord はそのための入り口（UI）であって、AI のロジックそのものではない。

> 補足：これは「100 本の AI が同時に会話しながら走る」ような大量並列の話ではない。実際には Claude Code が応答を待っている時間が多く、人間（yousan）が次の指示を出すまでが追いつかず、そこで詰まることも多い。本当の価値は「同時に何本も全力で走る」ことより、**複数のセッションを開いたままにして文脈を失わず、いつでもすぐ続きから再開できる**ことにある。

## 誰のため（利用者像 = yousan）

**サーバーに Claude Code を常駐させ、手元（Mac やスマホ）から複数のセッションを並行して進めたい開発者。具体的には yousan 本人。**

- Web 中心の開発者であり、インフラもやる（FreeBSD、Ubuntu/Debian、GNU screen を長く使ってきた）。
- ラップトップを持って喫茶店など外で開発するのが好き。だが外の回線は不安定で、大きいファイルや画像のやり取りに弱く、移動するとラップトップ上の Claude Code が落ちてしまう。
- そこで、Claude Code をサーバーに常駐させ、手元の端末からつなぐスタイルに移った（例として大容量メモリの自宅サーバーを使っているが、これはあくまで一例。クラウドのサーバーでもよいし、Unix 系でなくてもよい）。
- 扱う対象はコードだけではない。複数のリポジトリに加えて、ブログ更新、チャットボット、文章の構成、サーバーの運用監視（Prometheus / Grafana でリソースを見る、アラート、ミドルウェアの管理）まで。気づくと何本も並行している。
- 仕事の出し方：1 つタスクを投げると返ってくるまで時間がかかる。その間に別のタスクを進める、を何本か同時に回す。

**この人物が「使っていて不便か」を、内部実装を知り尽くした開発者目線ではなく、利用者目線で確かめる** — それが C-lord の評価の軸。

> 出典：この利用者像と動機は yousan 本人の音声コメント（#288）に基づく。並行している本数や戻り時間などの数字は「だいたいの規模感」として扱い、決まった値として断定しない。

## 一番解決したい痛み

**生の SSH + tmux で何本もの Claude Code を回すと、管理がすぐ破綻する。**

具体的には次の連鎖で苦しくなっていた：

1. **セッションが切れる** — 外の回線が落ちると、サーバー上の Claude Code 作業が巻き添えで死ぬ（tmux の attach / detach で延命はできても、手間は残る）。
2. **どこで何をさせているか覚えられない** — 1 つのセッションに複数のウィンドウがあり、それが何本もある。Mac のタブ → SSH → tmux attach → ウィンドウ移動、という何段もの切り替えを並行ぶん繰り返す。
3. **過去を辿るのがつらい** — 「自分が何を言い、Claude がどう計画し、どう動き、結果どうなったか」を tmux で逆スクロールして探すのは、とても重い。
4. **画像やファイルの壁** — リモートの Claude Code に画像を渡すのが難しい（Mac のターミナル → tmux のクリップボード経路がつながらず、毎回 Web に上げて URL を渡していた）。逆に Claude が作った画像を手元で見るのも難しい。

→ これらを、**Discord を Claude Code + tmux の入り口にする**ことで解消する、というのが C-lord を作った動機（音声コメント #288）。

> 前向きな効能：C-lord が整ってきた結果として、**tmux を直接扱えない人でも Claude Code を扱いやすくなった**。これは元々の動機に後からついてきた価値で、利用者の裾野を広げる。

## 中心的な価値（痛みをどう解消するか）

### A. 切れない・どこからでも・複数を並行して進められる（これが核）

サーバーに Claude Code を常駐させ、Discord 越しにつなぐ。回線が切れても tmux のおかげでセッションは生き続ける（screen 時代から続く「切れない端末」への愛着がそのまま設計に流れている）。Mac でもスマホでも、サーバーと C-lord が動いてさえいれば届く。複数のセッションを開いたままにしておけるので、文脈を失わずにいつでも続きから再開できる。

**A は「手段」ではなく核そのもの。**「切れない」「どこからでも」「複数を文脈ごと保てる」は C-lord が存在する理由であり、ただの実装手段に格下げしない。

### B. リモートで結果から判断するには、判断できる形で結果が見えないといけない（A の必須条件）

リモートで複数のセッションをまとめて扱う（A）なら、手元には端末の生の情報がない。AI がコードを書き、人は端末ではなく Discord やスマホから「結果」を見て判断する。**だとすれば、判断できる形で結果が見えていなければならない。**

- 「いま何が起きているか」
- 「報告された問題は、本当に起きるのか」
- 「直ったのか」

これらが **Discord 側で実際に見られて・再現できる**こと。これは #287 が言う「確認できないギャップ」のことで、具体的には：

- **(1) あるべき動きの決まりが無い** — 「本来どう動くべきか」を書いた単一の決まりが無く、仕様かバグかを見分けられない。
- **(2) 報告がコードの言葉になる** — `thread_state_sync` / `pytest 37/37` / 関数名・行番号で語られ、「利用者から見て何がどう変わったか」に翻訳されない（特に C-lord 自身を直す PR で起きやすい）。
- **(3) 確認できない** — Discord の実画面（レイアウト・別の吹き出しか同じ吹き出しか・ランプの色）が画像で残らず、「たぶんそう」止まりで確証が持てない。

### C. 誰のインスタンスでも設定なしで動く共通土台（OSS として保つ）

C-lord は OSS のフレームワークとして公開している。公開している以上、**個人や組織が自分の Discord に Claude Code を載せられる、設定不要でいつも予想どおりに動く共通土台**を保つことを目標にする。C は「これから尖らせる方向」ではなく、「公開物として守るべき品質」。

### 効能（A・B・C が形になると何がうれしいか）

C-lord は tmux の構造を Discord の構造にそのまま 1:1 で写す：

| tmux | Discord | Claude Code |
|------|---------|-------------|
| **セッション** | **チャンネル** | （その束） |
| **ペイン / ウィンドウ** | **スレッド** | **1 セッション** |

- **1 チャンネル = 1 tmux セッション。**
- **1 スレッド = 1 ペイン = 1 Claude Code セッション。スレッドでのやり取りが、そのまま Claude Code とのやり取りになる。**

これで効能が出る：

- **見通しが良くなる**（痛み 2・3 への答え）。tmux を逆スクロールする代わりに、Discord の履歴をスワイプやホイールで辿れる。どれが何の作業か、自分の発言と Claude の計画・結果がどう対応するかが分かりやすい。
- **セッションが切れなくなる**（痛み 1 への答え）。回線が落ちてもサーバー側のセッションは生き続け、つなぎ直せば続きから。
- **画像やファイルが双方向に届く**（痛み 4 への答え）。Discord に画像やファイルを貼れば Claude に届くし、Claude が作った画像も Discord でそのまま見られる。細かい仕様は今後 #287 の作業で詰める。

## 今の優先順位

C-lord は A・B・C の順で考える。ぶつかったら上を優先する：

1. **A（切れない・どこからでも・複数を文脈ごと並行）= 核。** これを損なう変更は、便利でも入れない。
2. **B（結果が判断できる形で見える）= A の必須条件。** リモートで判断するには、結果が見えて初めて成り立つ。「テストが緑だから完了」では A が機能しない。
3. **C（設定不要で予想どおりに動く OSS の共通土台）= 維持。** A と B を、特定の個人に依存せず・壊れにくく・設定不要な形で提供し続ける。

**速さと「いつも予想どおりに動くこと」について：今は速く出すことを優先してよい。** ただし速さと予想どおりであることは対立ではなく、段階で切り替わる。

- **やると合意した作業は止まらず自走してよい** — PR → 手動QA → マージ → 本番デプロイ → 本番での実測まで、いちいち止まらなくてよい。
- **ただし起点の問い（「これは仕様? バグ?」「なぜこうなる?」）はまだ作業ではない。** まず答えてから着手する。
- 設計を変える・壊す操作・取り返しのつかない判断は、推測で走らず一行で確認する。

## やらないこと

- **個人 bot にはしない。** 個人設定・秘密・特定サーバー固有のロジックは C-lord に入れない。それらは利用者のインスタンス側に置く。
- **AI のロジックを持たない。** プロンプト設計・ツール定義・メモリ管理・system prompt は持たない。C-lord は**ブリッジ**であり、それらは Claude Code が担う。
- **TUI スクレイプを復活させない（#53）。** Claude は Skill 経由で自分の最終回答を `POST /api/reply` する。tmux の画面からテキストを抜いて Discord に流す経路は、構造的に作らない（TUI のゴミが混ざるバグの温床だった）。
- **tmux を置き換えるための高機能 TUI ではない。** C-lord は tmux を消すのではなく、tmux を Discord からまとめて扱えるようにするブリッジ（tmux のペインは人間が直接見るために残る）。
- **Anthropic API を直接は呼ばない。** Claude Code CLI を subprocess として起動する（CLAUDE.md・skills・memory・MCP・hooks をまるごと引き継ぐため）。
  - 補足：先日のアップデートで Claude Code の `-p`（print）オプションが専用枠のクレジット方式になる予定だが、この方式でも CLI subprocess の作りのまま対応できる見込み。

## 「仕様か、バグか」の見分け方

「これは仕様か、バグか」「この変更は入れるべきか」を聞かれたら、コードや好みではなく、次の順で見分ける。**質問を黙って作業に変えない。まず見分けて、合意してから着手する。**

> 注意：この手順は、決まり（あるべき動きの一覧）がまだ無いときに「仮置きして進める」やり方であって、決まりの不在そのものを埋めるものではない。各機能のあるべき動きの一覧は別途まとめる（#287 P1）。

### 手順

1. **あるべき動きを先に決める** — その機能が「本来どう動くべきか」を、決まり（あれば）から探す。決まりが無ければ、まず「決まりが無い」と正直に言い、理念に照らしてあるべき動きを仮置きする。**仮置きしたあるべき動きは、実際の動きを見る前に文章で固定する。** 見た結果に合わせて後から動かさない（後から都合よく寄せられるのを防ぐため）。現状のコードは「あるべき動き」の答えにはならない — コードは意図を語れないので。
2. **実際の動きを見る** — staging で実際に動かして確認・再現する。Discord の実画面（ユーザー提供のスクリーンショットが主）＋ tmux のキャプチャ＋ REST で取ったメッセージ本文で「本当の動き」を掴む。コードを読む前に、利用者目線で「使って不便か」を見る。
3. **仕様かバグか答える** — 見た実際の動きと、手順1で固定したあるべき動きを突き合わせ、「仕様どおり」か「バグ」かを**先に答える**。
4. **食い違いを切り分ける** — ズレがあったら、それが
   - **(a) 理念を見直すべきもの**（理念が現実に合っていない）か、
   - **(b) 例外として許すもの**（理念は正しいが今回は意図的に外す）か、
   - **(c) 技術的にまだできないだけ**（理念どおりにしたいが今はできない）か、
   を分けて示す。

### 例

**例1：「テストが緑だから完了」と報告された。**
- 理念に照らす → B（結果が見える）が必須条件。CI は ruff / pyright / pytest（モック）しか回らず、tmux・Discord・再起動の継続といった実際の動きは確認されない。**緑の CI ＝ 動く、ではない。**
- 答え → 「テスト緑」は必要なだけで、完了ではない。完了は staging で「直す前は再現する → 直した後は再現しない」を確認し、Discord の実画面の証跡（ユーザースクショが主＋ tmux / REST で補強）が残って初めて成立する。

**例2：「ここで選択肢が出てないけど、なぜ?」と聞かれた。**
- これは見分けの依頼であって、作業の指示ではない。すぐコードを読んで「直します」「PR 作りました」と走り出すのは、認識がズレたまま実装してしまう恐れがあり、B（確認できること）の趣旨に反する。
- 手順どおり → あるべき動きを決め（そこで選択肢が出るべきなのか）→ 実際の動きを見て（本当に出ていないか、出るべき場面か）→ **「これは仕様です／バグです」をまず一行で答える** → そのうえで「直すか」を合意してから着手する。

## 理念の限界

理念が決められるのは「誰があるべき動きを決めるか（最終的には yousan）」と「決まりが無いとき何に照らして仮置きするか」まで。**各機能のあるべき動きそのものは、理念からは出てこない。** それは「あるべき動きの一覧」として別途まとめる（#287 P1）。理念はその一覧を**見分けるための基準**を与えるが、一覧の**中身を産むものではない**。
