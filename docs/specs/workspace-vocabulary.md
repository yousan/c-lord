# あるべき動き: ワークスペースの用語とライフサイクル通知

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

決定の経緯は #540、実装は #571。

## なぜこの文書があるか

**1つの概念に4つの名前が付き、1つの語が3つの実体を指していた。**

2026-08-26 に `c_lord/` を実測したところ:

| 語 | 日本語 UI での出現 | yousan の発言 3015 件での出現 |
|---|---:|---:|
| スレッド | 34 | 373 |
| セッション | 19 | 143 |
| **ワークスペース** | **2**（どちらも添付ファイルの保存先の話で、この概念とは無関係） | 22 |

つまり **c-lord は「ワークスペース」という語を一度も利用者に教えていないのに、コマンド名にはその語を使っていた**。同時に、隣り合う文言が同じ状態を別の名詞で説明していた:

```
"ℹ️ このスレッドは終了しています（`[終了]`。tmux ウィンドウもありません）。"
"ℹ️ この作業セッションは現在停止しています（tmux ウィンドウがありません）。"
```

## 用語（確定）

**ワークスペース = 1つのスレッドに紐づく作業一式を束ねた呼び名。**

| 見る場所 | 呼び名 | 実体 |
|---|---|---|
| Discord から見ると | **スレッド** | チャンネル内のスレッド |
| Claude Code から見ると | **セッション** | `session_id` / transcript |
| ファイルシステムから見ると | **作業ディレクトリ** | `c-lord-sessions/<ch>/<thread>/` |
| docker から見ると | **開発環境** | その作業ディレクトリから立てたコンテナ |
| **これら全部を束ねた紐付け** | **ワークスペース** | 上記の対応関係そのもの |

### 書き方のルール

- **利用者向けの文言では常に「このスレッドのワークスペース」と書く。** 単独で「ワークスペースを停止しました」とは書かない。**知っている語（スレッド）から、知らない語（ワークスペース）へ橋を架ける**ため
- **「作業セッション」は使わない。** 廃止済み
- **ワークスペースを指して「セッション」と言わない。** 「セッション」は Claude の `session_id` と tmux セッションに予約する（1語1実体）
- 「スレッド」は容器の名前として使い続ける。利用者の第一言語（373回）だから

## 通知は「ラベル」ではなく「棚卸し」

**すべてのライフサイクル通知は、止まったものと同時に「まだ残っているもの」を必ず並べる。**

なぜか: スリープと停止は**自動で発火する**。利用者は頼んでいないので、最初に湧く疑問は「**何か失ったのか?**」になる。その答えを通知そのものに書くのが、どんなドキュメントより安く、しかも利用者が既に見ている場所で答えられる。

```
🛑 このスレッドのワークスペースを停止しました
💤 7日間 操作が無かったため自動で停止しました。      ← 自動のときだけ増える1行
▶️ 再開するには /workspace-start。このスレッドに投稿しても再開できます。

   Claude              ⏹ 停止
   開発環境 (docker)    ⏹ 停止（:55322 :55323 を解放）
   作業フォルダ          ✅ そのまま
   会話履歴             ✅ そのまま
   DBのデータ (volume)   ✅ そのまま
```

### 常に守ること

- **会話履歴と docker volume は、削除を含むどの操作でも消えない。** 通知は毎回そう言う
- **`開発環境 (docker)` の行は、コンテナが無くても「— （なし）」と出す。** 棚卸しの行を黙って減らさない
- **自動と手動で変わってよいのは説明の1行だけ。** 棚卸しの中身は完全に同一

最後の項目は構造で担保する。同じ結果になる文面を2箇所に書くと必ずズレる — #538 がまさにその事故（挙動を案内する側と実装する側で条件が食い違った）だった。だから通知は `c_lord/workspace_notice.py` の **1つの関数**が組み立て、`reason` 引数は説明行しか変えられない。

## 3操作（#540 合意）

**上の操作は下を含む**: 削除 ⊃ 停止 ⊃ スリープ

| | 操作 | 何をするか | 手動 | 自動 | 逆操作 |
|---|---|---|---|---|---|
| 1 | **スリープ** | claude を止める | なし（気づかれないのが目的） | 4時間 無操作 | 投稿するだけ（無言復元） |
| 2 | **停止** | スリープ ＋ docker も止める | `/workspace-stop` | 7日 無操作 | `/workspace-start` |
| 3 | **削除** | 停止 ＋ 作業ディレクトリも消す | `/workspace-delete` | 30日 かつ worktree クリーン | 投稿で再 clone |

### 自動停止の測り方（実装上の落とし穴）

**tmux の `window_activity` をアイドル判定に使ってはいけない。** Claude の TUI は
スピナーとステータス行を描き続けるので、**誰も触っていなくても更新され続ける**。
本番実測では、生きている 51 本すべてが「直近1〜3時間以内に activity あり」に
見えた。

判定は **最後の人間の発言**（`sessions.last_used_at`）を見る。

あわせて、以下は絶対に停止しない:

- **既に停止済みのもの** — 毎tick 通知を再投稿し続けてしまう
- **ターンが走っているもの** — `last_used_at` はターンの**開始**時刻なので、
  1週間走り続けているターンはタイムスタンプ上アイドルに見える。殺せば実作業が飛ぶ
- **タイムスタンプが壊れているもの** — 日付のパースに失敗したという理由で
  何かを破壊してはいけない

### 対象スレッドは「ほぼ必ず Discord 側でアーカイブ済み」である

Discord は放置されたスレッドを自動アーカイブする。**自動停止が選ぶ対象は、定義上その期間を超えている** — 7日放置されているのだから。つまり **対象はほぼ必ずアーカイブ済み**だと考えてよい。

これを踏まえないと動かない:

- **`bot.get_channel()` はキャッシュしか見ない。** アーカイブ済みスレッドは `None` が返る。`fetch_channel()` で取り直すこと
- **解決を試みる前に件数を絞ってはいけない。** 「古い順に N 件」で切ると、先頭が引けない限り後ろに永久に到達しない。上限は**実際に停止できた数**で数える
- **スキップは INFO 以上で記録する。** DEBUG に落とすと本番で見えず、「対象 93 件、5 件停止します」だけが出て**動いているように見える**

実際に #604 でこの3つが重なり、**自動停止は本番で4日間 1 件も動かないまま、正常に見えるログを出し続けた**。入力側の数（対象件数）だけでなく**出力側の数（実際に停止した件数）を必ず出す**こと。

### 削除には掃除が二つある（#613）

上の表の「削除」は **`sessions` の行を消すときに、その行が指すディレクトリも一緒に消す**。
だから **行を先に失ったディレクトリには、その仕組みは永久に届かない。** 行は Discord
スレッドと作業コピーを結ぶ唯一の handle なので、行が消えた時点でディレクトリは
誰からも参照されなくなり、しかし誰も消さない。

本番実測（2026-08-31）: 作業ディレクトリ 625 件のうち **313 件・17.3 GB が行を持たない**。

二つ目の掃除はそれを拾う。**6時間ごと**に走り、消すのは3つすべてを満たすものだけ:

1. `sessions` にその `working_dir` を持つ行が**無い**（停止済みの行も「有る」に数える）
2. git の worktree が**クリーン**
3. **30日以上**触られていない（ディレクトリと `.git` の新しい方の mtime で測る）

**残す方に倒す判定**（消しすぎは取り返しがつかない。消しそびれた GB は次の掃除で拾える）:

| 状況 | どうするか | なぜ |
|---|---|---|
| 未コミットの変更がある | **残す** | 失われた作業は戻らない |
| git ですらない | **残す** | クリーンか確かめる手段が無く、残骸と生成物を区別できない |
| `<root>/<数字>/<数字>` の形でない | **見ない** | root の下の他人のディレクトリは管轄外 |
| シンボリックリンク | **辿らない** | リンク先の本体を消すのが最悪の事故 |
| DB が読めない | **何もしない** | 行の一覧が空に見えると、生きているものが全部孤児に見える |

**上限は「実際に消せた数」で数える**（#593 の教訓）。試行回数で数えると、先頭に
消せないもの（本番では 313 件中 206 件）が並んだときそこで打ち止めになり、後ろに
永久に到達しない。

期間を Claude Code の `cleanupPeriodDays` から読まないのは意図的。行スイープは
「Claude が会話を忘れたらチェックアウトも役目を終える」という対応関係で期間を
揃えたが、**孤児には対応する行も transcript も無い**。揃える相手がいないものを
揃えたことにはしない。

### 持ち主のいない docker コンテナは「消さずに、見えるようにする」（#612）

同じ掃除のたびに、**どのワークスペースにも属さない docker コンテナ**を一覧して
ログに出す。**止めはしない。** 中身は誰かのデータで、勝手に落とす判断は
ディレクトリの削除より重い。まず「在ることが分かる」状態にする。

紐付けは `dev_environments` テーブルに残す。**停止する直前に書く** — そこが
「このコンテナはこのスレッドのもの」と分かる最後の瞬間だから。ワークスペースが
消えた後、`:55322` を誰が掴んでいるかに答えられるのはこの行だけになる。

### 「作ったが繋いでいない」を二度とやらない（#570 → #612）

**同じバグを2回踏んだ。** #570 は tmux リーパーが定義だけで呼ばれず空ウィンドウが
175本溜まった。#573 は `DevEnvRepository` と `orphaned_containers()` が同じ形で
死んでいて、本番 DB に `dev_environments` テーブルすら作られていなかった。

**どちらも単体テストは緑だった。** 単体テストは「関数が正しく動く」ことしか見ない
ので、**呼び出し元の不在は関数の振る舞いに一切現れない**。

だから `tests/test_wiring.py` が **参照そのもの**を検査する — 定義元モジュールの外に
その名前を使っている場所が1つ以上あるか。粗い判定だが、粗いからこそ「配線を忘れた」
という粗いミスに効く。**常に動いているべきものを足したら、必ずその表に足すこと。**

### スリープだけの例外

スリープは**利用者に気づかれないこと**がゴールなので、通常は何も出さない。**例外は1つだけ**: docker が動いていたら1行残す。

スリープは docker を止めない（走っているビルドや DB が飛ぶため）。つまり**ポートを掴んだまま**になる。これは利用者が自力で気づけず、かつ次に環境を立てるとき衝突として跳ね返ってくる、**唯一「知らないと困る」情報**。
