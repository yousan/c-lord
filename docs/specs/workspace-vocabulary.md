# あるべき動き: ワークスペースの用語とライフサイクル通知

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

決定の経緯は #540、実装は #571。

## なぜこの文書があるか

**1つの概念に4つの名前が付き、1つの語が3つの実体を指していた。**

2026-08-26 に `c_lord/` を実測したところ:

| 語 | 日本語 UI での出現 | yousan の発言 3015 件での出現 |
|---|---:|---:|
| スレッド | 34 | 373 |
| セッション | 19 | 143 |
| **ワークスペース** | **2**（どちらも添付ファイルの保存先の話で、この概念とは無関係） | 22 |

つまり **c-lord は「ワークスペース」という語を一度も利用者に教えていないのに、コマンド名にはその語を使っていた**。同時に、隣り合う文言が同じ状態を別の名詞で説明していた:

```
"ℹ️ このスレッドは終了しています（`[終了]`。tmux ウィンドウもありません）。"
"ℹ️ この作業セッションは現在停止しています（tmux ウィンドウがありません）。"
```

## 用語（確定）

**ワークスペース = 1つのスレッドに紐づく作業一式を束ねた呼び名。**

| 見る場所 | 呼び名 | 実体 |
|---|---|---|
| Discord から見ると | **スレッド** | チャンネル内のスレッド |
| Claude Code から見ると | **セッション** | `session_id` / transcript |
| ファイルシステムから見ると | **作業ディレクトリ** | `c-lord-sessions/<ch>/<thread>/` |
| docker から見ると | **開発環境** | その作業ディレクトリから立てたコンテナ |
| **これら全部を束ねた紐付け** | **ワークスペース** | 上記の対応関係そのもの |

### 書き方のルール

- **利用者向けの文言では常に「このスレッドのワークスペース」と書く。** 単独で「ワークスペースを停止しました」とは書かない。**知っている語（スレッド）から、知らない語（ワークスペース）へ橋を架ける**ため
- **「作業セッション」は使わない。** 廃止済み
- **ワークスペースを指して「セッション」と言わない。** 「セッション」は Claude の `session_id` と tmux セッションに予約する（1語1実体）
- 「スレッド」は容器の名前として使い続ける。利用者の第一言語（373回）だから

### どこまで直したか（見直し範囲 — #145）

「セッション」の2義（tmux セッション / c-lord の論理的な紐付け）の整理は、**利用者に見える文言だけ**を対象にした。内部の識別子は変えていない。

| 範囲 | 対応 | 理由 |
|---|---|---|
| 利用者向け文言（コマンド help・通知・エラー文、`c_lord/` 内の日本語文字列） | **済** — 「作業セッション」は 0 件（`grep -rn 作業セッション c_lord/`）、紐付けは「このスレッドのワークスペース」と書く（#571） | 利用者が混同するのはここ |
| 利用者向けドキュメント（`docs/COMMANDS.md` の通知例など） | **済** — 実際の文言に揃えた（#145） | ドキュメントが古い語を教え直さないため |
| コマンド名 | **済** — `/workspace-*`（#578。旧名はエイリアスで残る） | 利用者が打つ語 |
| 内部識別子（`sessions` テーブル、`SessionRepository`、`session_id`、`session_dir.py`、`c-lord-sessions/` ディレクトリ） | **変えない** | 1行が「スレッド ↔ Claude の `session_id`」の対応なので、`session` は上の「Claude Code から見ると **セッション**」の意味で正しい。改名は DB マイグレーションと利用者のパス変更を伴い、得るものが無い |
| コードコメント | **変えない**（見つけたら直す程度） | 利用者の目に触れない。全置換は差分が大きいだけで誤操作リスクを減らさない |
| `docs/STAGING.md` の「作業セッション」 | **対象外** | tmux の話（「c-lord と無関係な作業セッションまで全滅する」）で、この概念を指していない |

## 通知は「ラベル」ではなく「棚卸し」

**すべてのライフサイクル通知は、止まったものと同時に「まだ残っているもの」を必ず並べる。**

なぜか: スリープと停止は**自動で発火する**。利用者は頼んでいないので、最初に湧く疑問は「**何か失ったのか?**」になる。その答えを通知そのものに書くのが、どんなドキュメントより安く、しかも利用者が既に見ている場所で答えられる。

```
🛑 このスレッドのワークスペースを停止しました
💤 7日間 操作が無かったため自動で停止しました。      ← 自動のときだけ増える1行
▶️ 再開するには /workspace-start。このスレッドに投稿しても再開できます。

   Claude              ⏹ 停止
   開発環境 (docker)    ⏹ 停止（:55322 :55323 を解放）
   作業フォルダ          ✅ そのまま
   会話履歴             ✅ そのまま
   DBのデータ (volume)   ✅ そのまま
```

### 常に守ること

- **会話履歴と docker volume は、削除を含むどの操作でも消えない。** 通知は毎回そう言う
- **`開発環境 (docker)` の行は、コンテナが無くても「— （なし）」と出す。** 棚卸しの行を黙って減らさない
- **止まっている（exited）コンテナしか無いときも「— （なし）」と出す**（#1182）。`/workspace-stop` → `/workspace-delete` の順だと `docker ps -a` は exited のコンテナを見つけるが、ポートも掴んでおらず止めるものも無い。以前はこれを「▶️ 動いたまま」と出し、後始末が失敗したように読めた。「▶️ 動いたまま」は、ポートを掴んだままのコンテナ（`running` に加えて `paused`・`restarting`。`exited`・`created`・`dead` 以外）が残ったときだけ。`paused`・`restarting` は止める対象にしていないので、残っていれば「動いたまま」と出す（「なし」と言うと、ポートを握ったままなのに無いと読める）。スリープの通知（コンテナは止めない）も同じで、ポートを握ったままのコンテナがあれば、paused・restarting でもそのポートを挙げる
- **「⏹ 停止（:N を解放）」に挙げるのは、この操作で止めたコンテナのポートだけ**（#1221）。前から exited だったコンテナはポートを握っていなかったので、そのポートは「解放」に入れない。以前は `docker ps -a` が見つけた全コンテナのポートを並べ、元から空いていたポートまで「解放」と書いていた
- **自動と手動で変わってよいのは説明の1行だけ。** 棚卸しの中身は完全に同一

最後の項目は構造で担保する。同じ結果になる文面を2箇所に書くと必ずズレる — #538 がまさにその事故（挙動を案内する側と実装する側で条件が食い違った）だった。だから通知は `c_lord/workspace_notice.py` の **1つの関数**が組み立て、`reason` 引数は説明行しか変えられない。

## 3操作（#540 合意）

**上の操作は下を含む**: 削除 ⊃ 停止 ⊃ スリープ

| | 操作 | 何をするか | 手動 | 自動 | 逆操作 |
|---|---|---|---|---|---|
| 1 | **スリープ** | claude を止める | なし（気づかれないのが目的） | 4時間 無操作 | 投稿するだけ（無言復元） |
| 2 | **停止** | スリープ ＋ docker も止める | `/workspace-stop` | 7日 無操作 | **手動で止めたなら**「▶️ 再開する」/ `/workspace-start`。**自動で止まったなら投稿するだけ**（1行出て実行、#700） |
| 3 | **削除** | 停止 ＋ 作業ディレクトリも消す | `/workspace-delete` | 30日 かつ worktree クリーン | 投稿で再 clone |

`/workspace-delete` は `/workspace-stop` と**同じ後始末の関数**を通ってから作業ディレクトリを消す（#1113）。走っているターンを先に終え（#909）、開発環境の docker も止めて記録する（#574 / #612）。以前は delete だけがこの2つをせず、ターンが ❌ で終わり、持ち主のいないコンテナがポートを掴んだまま残った。delete の通知には docker の行（`🐳 開発環境 (docker): ⏹ 停止（:55322 を解放）`）が、コンテナがあったときだけ出る。

### 逆操作は「誰が止めたか」に従う（#700）

**c-lord が自動で止めたものは、投稿するだけで戻る。利用者が止めたものだけ、明示的に戻す。**

自動停止は利用者が頼んだものではありません。頼んでいない片付けの取り消しにボタンを押させるのは、
c-lord の都合を利用者に払わせているだけです。逆に手動停止は決定なので、
[session-close.md](session-close.md) の「自分で終わらせたなら、勝手に動き出さないでほしい」を守ります。

同じことが 30 日の**行スイープ**にも当てはまります（#818 以降、行は消さずに「片付け済み」として
残し、稼働中の扱いから外すだけ）。片付け済みになっても作業ディレクトリは残っている
ことが多く（本番実測 625 件中 313 件）、そのときは投稿するだけで繋ぎ直して実行します。

**復帰のときに出すのは 1 行だけ。** 上の「通知は棚卸し」ルールは**止めるとき**の話です。戻るときに
棚卸しを繰り返すと、ただの復帰が事故のように読めます。戻るときに要るのは「なぜ止まっていたか」
だけです。

### 自動停止の測り方（実装上の落とし穴）

**tmux の `window_activity` をアイドル判定に使ってはいけない。** Claude の TUI は
スピナーとステータス行を描き続けるので、**誰も触っていなくても更新され続ける**。
本番実測では、生きている 51 本すべてが「直近1〜3時間以内に activity あり」に
見えた。

判定は **最後の人間の発言**（`sessions.last_used_at`）を見る。

あわせて、以下は絶対に停止しない:

- **既に停止済みのもの** — 毎tick 通知を再投稿し続けてしまう
- **ターンが走っているもの** — `last_used_at` はターンの**開始**時刻なので、
  1週間走り続けているターンはタイムスタンプ上アイドルに見える。殺せば実作業が飛ぶ
- **タイムスタンプが壊れているもの** — 日付のパースに失敗したという理由で
  何かを破壊してはいけない

### 対象スレッドは「ほぼ必ず Discord 側でアーカイブ済み」である

Discord は放置されたスレッドを自動アーカイブする。**自動停止が選ぶ対象は、定義上その期間を超えている** — 7日放置されているのだから。つまり **対象はほぼ必ずアーカイブ済み**だと考えてよい。

これを踏まえないと動かない:

- **`bot.get_channel()` はキャッシュしか見ない。** アーカイブ済みスレッドは `None` が返る。`fetch_channel()` で取り直すこと
- **解決を試みる前に件数を絞ってはいけない。** 「古い順に N 件」で切ると、先頭が引けない限り後ろに永久に到達しない。上限は**実際に停止できた数**で数える
- **スキップは INFO 以上で記録する。** DEBUG に落とすと本番で見えず、「対象 93 件、5 件停止します」だけが出て**動いているように見える**

実際に #604 でこの3つが重なり、**自動停止は本番で4日間 1 件も動かないまま、正常に見えるログを出し続けた**。入力側の数（対象件数）だけでなく**出力側の数（実際に停止した件数）を必ず出す**こと。

### 削除には掃除が二つある（#613）

上の表の「削除」は **`sessions` の行を消すときに、その行が指すディレクトリも一緒に消す**。
だから **行を先に失ったディレクトリには、その仕組みは永久に届かない。** 行は Discord
スレッドと作業コピーを結ぶ唯一の handle なので、行が消えた（#818 以降は片付け済みになった）時点で
ディレクトリは誰からも参照されなくなり、しかし誰も消さない。片付け済みの行はディレクトリを
「持っている」扱いにしない — そうしないと、以前は孤児として拾えていたものが永久に残る。

本番実測（2026-08-31）: 作業ディレクトリ 625 件のうち **313 件・17.3 GB が行を持たない**。

二つ目の掃除はそれを拾う。**6時間ごと**に走り、消すのは3つすべてを満たすものだけ:

1. `sessions` にその `working_dir` を持つ行が**無い**（停止済みの行も「有る」に数える）
2. git の worktree が**クリーン**
3. **30日以上**触られていない（ディレクトリと `.git` の新しい方の mtime で測る）

**残す方に倒す判定**（消しすぎは取り返しがつかない。消しそびれた GB は次の掃除で拾える）:

| 状況 | どうするか | なぜ |
|---|---|---|
| 未コミットの変更がある | **残す** | 失われた作業は戻らない |
| **どの remote ブランチにも載っていないコミット**・stash がある（#903） | **残す** | `git status` には出ないが、push していない作業はここにしか無い |
| **git が無視するファイル**がある（`.env`・`info/exclude` で隠した手順書など — #903） | **残す**（再生成できるものと c-lord のものは除く — 下の「#903」） | `git status` には出ないが、利用者が置いたものかもしれない |
| 変更が **c-lord 自身が置いたファイルだけ** | **消す** | 下の「c-lord の持ち物は作業に数えない」 |
| git ですらない | **残す** | クリーンか確かめる手段が無く、残骸と生成物を区別できない |
| `<root>/<数字>/<数字>` の形でない | **見ない** | root の下の他人のディレクトリは管轄外 |
| シンボリックリンク | **辿らない** | リンク先の本体を消すのが最悪の事故 |
| DB が読めない | **何もしない** | 行の一覧が空に見えると、生きているものが全部孤児に見える |

#### c-lord の持ち物は作業に数えない（#749）

c-lord は毎ターン `.claude/skills/discord-read/SKILL.md` を各ワークスペースに書く（#259）。
clone の `.gitignore` はそれを知らないので `git status` に untracked として出る。
**これを「未コミットの変更」と数えていた間、孤児スイープは 105 回連続で 0 バイトしか
回収しなかった**（2026-09-18 実測: 残した 80 件のうち 60 件・9.6 GB は変更がその
SKILL.md だけ）。同じ判定を使う 30 日スイープは、そういうスレッドに
「書きかけの成果物はディスク上にそのままあります」と案内していた。

いまは `git status` の各行を見て、次のものだけを**作業に数えない**:

| 行 | なぜ作業ではないか |
|---|---|
| `.claude/skills/discord-read/SKILL.md`（untracked、または追跡されていて作業ツリーだけ違う） | c-lord が毎ターン上書きする。そこに置いた編集は次のターンで必ず消える |
| `.claude/skills/discord-reply/` / `discord-prompt-choice/` 以下（#712 の残骸） | c-lord が毎ターンディレクトリごと消す |
| `.claude/clord-thread-history.md`（untracked、または追跡されていて作業ツリーだけ違う — #882） | 再接続（#538 / #700 / #862）のとき c-lord が書き出す Discord の過去ログ。利用者が書いたものではない |
| `.claude/worktrees/<name>/` で、**その worktree 自身がクリーン** | Claude Code のサブエージェントの worktree。中を開いて同じ規則で判定し、変更が1つでもあれば作業に数える |

それ以外 — `.claude/settings.local.json`、利用者自身の skill、`discord-read/` の隣に
置かれた別ファイル、**`git add` 済みの変更**（誰かの判断なので）— はすべて作業に数え、残す。

#### push していないコミットと、git が無視するファイル（#903）

`git status` が空でも消してよいとは限らない。**次の2つは `git status` に出ない**ので、
#903 まではどちらも「クリーン」と見なされて消えていた（2026-10-16 に本番コードで確認）:

- **どの remote ブランチにも載っていないコミット** — Claude がブランチに commit したが
  push していない作業。HEAD（detached を含む）と**手元の ref**（ブランチ・`refs/original`・`refs/keep/*` など。
  `refs/remotes/*`・別に数える stash・タグ・notes を除く）から辿れて、`refs/remotes/*` のどれからも辿れないコミットを数える
  （#1198。以前はブランチと HEAD だけを見ていて、`refs/original` などにしか無いコミットを消していた）。
  タグと notes を数えないのは、fetch したもの（push したもの）と手元だけのものを見分けられず、数えると
  `git fetch --tags` や notes を取り込んだワークスペースを永久に残してしまうため。タグや notes にしか無いコミットは
  消える（既知の限界）。
  annotated tag を指す ref も中のコミットまで辿る（ref の名前のまま `git rev-list` に渡す）。
  - **ワークスペース自身のタグにしか無いコミットは数えない**（既知の限界。サブモジュールでは、タグにしか無いコミットも、上流に同じタグが無い限り数える — #1246）。
    手元では fetch したタグと手で打った `git tag wip` を見分けられず、タグを数えると、タグを取ってきただけの
    ワークスペース（`--depth=1` の clone のあとの `git fetch --tags`、消されたブランチに打たれたタグを持つ `--local` の clone）が
    すべて「未 push」になって消せなくなったため（`ls-remote` のブランチ先端では、shallow の境界の下や消えたブランチのタグを確かめられない）。
  1 件でもあれば残す。remote が1つも無いリポジトリでは全コミットがこれに当たる（他にどこにも無いので）。
  リンクされた worktree（`git worktree add --detach` で別の場所に作ったもの）の detached HEAD と、その worktree だけの ref
  （`refs/worktree/*`・`refs/bisect/*`、`.git/worktrees/<名前>/` の中のファイル。シンボリックリンクのディレクトリも git と同じく辿る）からも数える（#1198。以前は数えず、
  そのコミットをワークスペースごと消していた）。ファイルを読むだけで git の呼び出しは増えない。読めない・壊れているときは
  `unpushed commits unknown (git rev-list failed or worktree unreadable)` として残す。数える起点は標準入力で `git rev-list --stdin` に渡す（ref が何万あってもコマンドラインがあふれない）。
  - **git の呼び出しはどれも 60 秒で打ち切り、打ち切りは「分からない」として残す**（#1198。`git clone` だけは打ち切らない）。
    打ち切るときは、git が起こしたサブモジュールの `git status` やフィルタもまとめて止める（git は自分のプロセスグループで動かす）。
    remote に聞く `git ls-remote` も同じで、打ち切ると ssh・`git-remote-https`・`upload-pack` などの子もまとめて止める（打ち切りは 20 秒のまま）。
    調べるだけの git は任意のロックを取らない（`GIT_OPTIONAL_LOCKS=0`。`git status` が `index.lock` を持ったまま止められると、
    残したワークスペースで次の `git commit` が失敗していた）。`git status` 自体が打ち切られたときの理由は `status unknown (git timed out)`（「git リポジトリではない」とは書かない）。
    「分からない」を「stash 無し」「ブランチ無し」「サブモジュール無し」と読む箇所は無い。partial clone（`--filter=blob:none`）で
    オブジェクトが欠けていても、調べる途中でネットワークから取りに行かない（`GIT_NO_LAZY_FETCH=1`。git 2.44 未満では効かず、そのときは打ち切りが守る）。
  - **サブモジュールのブランチを push したあと remote 側で消しても、手元に残った古い `refs/remotes/origin/<branch>` を
    「push 済み」の証にしない**（#1245。以前は信じて、閉じた PR のブランチにしか無かったコミットをワークスペースごと消していた）。
    サブモジュール（チェックアウトの無い `.git/modules` の git ディレクトリ・入れ子のリポジトリ・下の「無視されたディレクトリの中の
    リポジトリ」も同じ）の数えが 0 のとき、**ほかに残す理由が何も無い場合だけ**、そのリポジトリの remote-tracking ref を確かめる。
    - **確かめるのは、このクローンで作ったコミットを持つ追跡 ref だけ**（#1245 の3回目のレビュー）。「このクローンで作ったコミット」は
      このクローン自身の reflog（`logs/HEAD`・`logs/refs/heads/*`・リンクされた worktree の `logs/HEAD`）の、`commit`（`amend`・
      `merge`・`initial` を含む）・`cherry-pick`・`revert`・`am` の行と、`rebase`・`pull --rebase` で書き直したコミットの行
      （`pick`・`reword`・`squash`・`fixup`・`edit`。`(start)` は上流を checkout するだけ、`(finish)` は最後の先端 — 何も書き直さない
      同期では上流の先端そのもの — なので除く）、`merge`・`pull` の行（`: Fast-forward` で終わるものは除く）が書いたコミットと、
      `logs/refs/stash` のすべての行（stash は必ずここで作る）。判定するのはメッセージの最初の `": "` より前（操作の名前）だけで、
      後ろのコミットの件名に "fast-forward" や "(start)" と書いてあっても数えるのをやめない（#1245 の4回目のレビュー。以前は件名で
      読み違えて、そのコミットを消していた）。それを持つ追跡 ref は、push したかどうかに関わらず確かめる —
      URL を直接指定して push してから fetch した、別名の remote（同じ URL）に push してから origin を fetch した、push したブランチが
      上流で `release` に fast-forward され、それを fetch した、のどれでも、作ったコミットは fetch した追跡 ref の下にあるため。
      reflog に `update by push` がある追跡 ref も確かめる（念のため）。それ以外の追跡 ref は remote から来たものしか持たないので
      そのまま信じ、ネットワークには聞かない。だから**手元で何もしていないサブモジュールは、上流の `main` が進んでも、上流の
      ブランチが force-push されても（`dependabot/*` など）、消されても、ネットワークに出ずに消せる**（`ls-remote` は 0 回）。
      費用は reflog のファイル読みと、作ったコミットがあるときだけ `cat-file`・`for-each-ref --contains` を1回ずつ。
    - **HEAD の reflog が無い・空・読めない、または ref の更新を記録しない設定（`core.logAllRefUpdates=false`）のときは、
      どれを作ったか分からないので、すべての追跡 ref を確かめる**（`reflog expire --expire=now --all` のあと、reflog を書かない
      ツール（go-git・dulwich など）で作業したリポジトリ）。上流が手元に無いコミットへ進んでいれば「分からない」として残す
      （記録しない設定のリポジトリでの「残しすぎ」として受け入れている）。
    - **既知の限界**: このクローンで作ったコミットの reflog の行が `gc.reflogExpire`（既定 90 日）より古くて期限切れになり、
      push の記録も期限切れになり、いまは上流で消されたブランチの fetch した追跡 ref だけが持っている場合は、作ったことが分からず
      信じて消す（HEAD の reflog にその後の行が残っている部分的な期限切れ）。**このとき、そのコミットの唯一のコピーが
      ワークスペースと一緒に失われる**（W57 の12回目のレビューで確認。受け入れている既知の限界）。
    - **既知の限界**: stash のコミットを URL を指定して push し（追跡 ref に push の記録が無い）、fetch したあと stash を drop すると、
      `logs/refs/stash` からその行が消えるので「ここで作った」と分からず、上流でブランチが消されると信じて消す。
    - **既知の限界**: 削除したリンクされた worktree（`git worktree remove`）で作ったコミットは、その worktree の reflog が一緒に
      消えるので「ここで作った」と分からない。そのコミットを URL を指定して push しただけ（追跡 ref に push の記録が無い）で、
      いまは fetch した追跡 ref だけが持っている場合は、上流でブランチが消されると信じて消す。
    - 確かめるときは、その追跡 ref が属する remote に `git ls-remote --heads` で聞く（ワークスペース自身の照合と同じ `_run`・
      20 秒の打ち切り・60 秒の使い回し）。証になるのは、そのブランチが remote にまだあって同じコミットを指しているときと、
      進んだ先の remote の先端のコミットが手元にあるとき（その先端から辿れるもの＝先端の祖先だけが載っている。force-push や
      消して作り直したブランチから外れたコミットは数えて残す）。
    - 確かめた追跡 ref（ここで作ったコミットを持つもの、または push の記録があるもの — W57 の12回目のレビューで
      `git push origin origin/main:refs/heads/release` のあと上流が進んだ場合も足した）のブランチが**手元に無いコミットへ**進んでいるときは、そのブランチだけを
      1回 fetch して確かめる（#1245 の4回目のレビュー。PR を merge してブランチを消し、`pull` したあと、誰かが上流の `main` に
      push しただけで、ずっと「分からない」になっていた）。fetch は一時ディレクトリに作る使い捨ての bare リポジトリに取る。
      そのリポジトリはワークスペースのオブジェクトを `objects/info/alternates` で借りるので、祖先かどうかはそこで確かめられ、
      **ワークスペースには ref もオブジェクトも設定も増えず、ワークスペースの hook や設定も一切動かない**（#1245 の5回目の
      レビュー）。タグ・`FETCH_HEAD`・サブモジュールは取らず、自動 gc もしない。`_run` を通るので打ち切り（`ls-remote` と同じ
      20 秒）・プロセスグループごとの停止・プロンプト無しは `ls-remote` と同じ。取った先端の祖先に元の追跡 ref の先端があれば証に
      なり、無ければ（force-push・消して作り直した）証にならず数えて残す。fetch が失敗・打ち切りなら
      `sub: unpushed commits unknown (remote branch moved to a commit not here)` として残す。答えは `ls-remote` と同じく 60 秒、
      （解決した URL・ブランチ・元の先端・remote の先端）ごとに使い回し、失敗は（解決した URL・ブランチ）ごとに使い回す（止まる
      remote で待つのは 60 秒あたり1回）。ここで作ったコミットを持たない追跡 ref と、作ったか分からないとき（reflog が使えない）は
      fetch しない（後者は「分からない」として残す）。partial clone の設定を書き換えないよう `--filter` は付けない。
      以前の版（3eaa7da）が使っていた `refs/clord-probe/*` は、手元の作業として数えず（掃除が途中で止まって残っても、ワークスペースを
      残し続けない）、見つかれば `.lock` ごと消す。ネットワークの回数は、手元で何もしていないサブモジュールは 0 回、PR の流れで上流が
      動いていなければ `ls-remote` 1回、動いていれば `ls-remote` 1回と fetch 1回。PR を merge commit で merge してブランチを
      消し、ワークスペースでは fetch していない場合は `ls-remote` 1回と（既定のブランチの）fetch 1回、fast-forward で merge した
      場合は `ls-remote` 1回だけ。
    - 確かめた追跡 ref のブランチが remote で消えていたら、それ自体は何の証にもならない。ただし、そこからしか辿れない
      コミットが残るときは、**remote のほかのブランチにそのコミットがあるかを同じ使い捨てのリポジトリへの fetch で確かめる**
      （W57 の12回目のレビュー。GitHub の既定の流れ — PR を merge commit で merge してブランチを消す — で、fetch していない
      ワークスペースが `sub: 1 unpushed commit(s) (remote branch deleted or rewritten)` のまま消えなくなっていた）。まず remote の
      既定のブランチ（`ls-remote --symref` の `HEAD`）を1回 fetch し、無ければすべてのブランチを1回 fetch して、どれかの祖先に
      あれば証にする。消えたブランチが同じ remote にいくつあっても、既定のブランチとすべてのブランチはそれぞれ1回だけ fetch し、
      すべてのコミットをその1回で確かめる。すべてのブランチの確認では、どのブランチにも無いコミットが1つ見つかった時点で
      やめる（残すにはそれで足りる。W57 の13回目のレビュー。以前は消えたブランチごとに取り直していた）。既定のブランチの
      fetch が失敗・打ち切りなら、その remote ではすべてのブランチの fetch もしない。失敗は URL ごとに 60 秒使い回すので、
      止まる remote で待つのは 60 秒あたり1回。手元にすでにある先端は fetch しない（手元で証になる）。ここで作ったか分からないとき（reflog が使えない）は
      fetch しない。どのブランチにも無ければ（#1245 そのもの）数えて `sub: 1 unpushed commit(s) (remote branch deleted or rewritten)`
      として残す。**squash マージされて remote で消された、
      自分が push したブランチは、ワークスペースを残し続ける。** `/workspace-delete` に強制して消す指定は無いので、消してよいと
      分かっているなら、その追跡 ref を消す（`git -C <ワークスペース>/sub remote prune origin`）か、ワークスペースのディレクトリを
      手で消す（安全側の「残しすぎ」として受け入れている）。
    - **remote の URL がワークスペースの中のパスなら、その remote は無いものとして扱う**（`vendor/up.git` を origin にした
      `vendor/lib`、origin を `build/mirror.git` に向け直したサブモジュールなど）。ワークスペースと一緒に消えるので、そこへの push は
      控えにならない。その remote の追跡 ref は push したものも fetch したものも証にならず、`sub: 2 unpushed commit(s) (only on a
      remote inside the workspace)` のように数えて残す。設定に無い remote の追跡 ref は、確かめる必要が無ければ信じ、あれば証にしない。
      **ワークスペース自身も同じ**（`backup` という remote を `build/backup.git` に向けて `work` を push した、など）: その remote の
      追跡 ref は引き算に使わず（`--remotes` からその remote を除く）、それ自体を手元の ref として数え、`ls-remote` もしない。
      `.claude/worktrees/<名前>/`（Claude Code の worktree）を開いて判定するときも、「中」かどうかは外側のワークスペースで測る。
      この判定のために、ワークスペースごとに `git config` を1回足す。
    - **remote にはワークスペースの外から、URL で聞く**（#1245 の5回目のレビュー）。`ls-remote` は解決した URL を渡して中立の
      ディレクトリ（空の一時ディレクトリを手で空の git ディレクトリにし、`GIT_DIR` でそれを指す — リポジトリを探しに行かないので、
      `TMPDIR` が誰かの git リポジトリの中にあっても、パスに `:` があっても、bot の環境に `GIT_DIR` があっても、その
      `core.sshCommand` や `insteadOf` は効かない。W57 の12・13回目のレビュー。12回目の `GIT_CEILING_DIRECTORIES` は `:` で
      区切られて効かなかった。その git ディレクトリの HEAD は `main` ではなく `clord-neutral-<乱数>` を指すので、bot の global の
      `includeIf "onbranch:main"` も当たらない — W57 の14回目のレビュー。`includeIf "gitdir:/**"` はどの git ディレクトリにも当たる
      ので効く。これは bot 自身の global の設定で、避けられない）で走らせるので、ワークスペースの設定（`remote.<name>.uploadpack`・`core.sshCommand`・credential helper・
      `insteadOf`）は効かない。bot の global の設定と環境（ssh の鍵・`GIT_SSH_COMMAND`・global の credential helper）は効くので、
      ふつうの ssh / https の remote はそのまま使える。調べるだけの git の呼び出しはすべて `core.fsmonitor=false`・
      `core.hooksPath=/dev/null`・`protocol.ext.allow=never` で走らせ（ワークスペースが仕込んだ fsmonitor のコマンドや hook は
      動かない。`-c` は git が起こすサブモジュールの git にも届く）、bot の秘密（`SENSITIVE_ENV_KEYS`、#353）は子プロセスの環境から
      除く。**bot の環境にあるリポジトリを指す変数**（`GIT_DIR`・`GIT_COMMON_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE`・
      `GIT_OBJECT_DIRECTORY`・`GIT_ALTERNATE_OBJECT_DIRECTORIES`・`GIT_NAMESPACE`・`GIT_CEILING_DIRECTORIES`・
      `GIT_DISCOVERY_ACROSS_FILESYSTEM`・`GIT_CONFIG`）も、調べるだけの git の呼び出しからはすべて除く（W57 の14回目のレビュー。
      `GIT_COMMON_DIR` があるとそのリポジトリの `core.sshCommand` が走り、`GIT_DIR` がクリーンなリポジトリを指していると、
      どのワークスペースもそのリポジトリとして読まれてクリーンと判定され、唯一のコピーごと消えていた）。呼び出しはそれぞれ
      `cwd` か `--git-dir` か、自分で渡す `GIT_DIR` でリポジトリを決める。clean/smudge フィルタ（`.gitattributes` と `filter.<名前>.clean`）は `git status` が走らせうる（既知の限界）。
    - remote に聞けない（失敗・打ち切り）ときは `sub: unpushed commits unknown (ls-remote failed)` として残す。聞くのは確かめる
      追跡 ref があるときだけなので、ネットワークの無いホストでも、手元で何もコミットを作っていないサブモジュールは妨げにならない。
    - 使い回しの鍵は remote の URL で、ローカルのパス（`../sub.git` など）はそのリポジトリの場所から解決した絶対パスにする
      （同じ相対 URL を持つ別のリポジトリが、互いの答えを使わない）。聞けなかったという答えも 60 秒使い回すので、ネットワークの
      無いホストが待つのは URL ごとに 60 秒あたり最大 20 秒（ワークスペースごとではない）。使い回しの 60 秒の間に remote で
      ブランチが消されると、その間は消える前の答えで判断する（既知の限界。間隔を短くしてあるのはそのため）。孤児の掃除
      （`cleanup_orphaned`）は一覧を作るときと消す直前に同じ判定を2回するが、2回目の `ls-remote` はこの使い回しで済む（受け入れている）。
    - 最初に理由が見つかった時点で聞くのをやめる（残すには1つで足りる）。費用はこの段に来たリポジトリ1つにつき、手元の
      `for-each-ref`・`config` の2回と reflog のファイル読み。push した追跡 ref があるときだけ remote の URL ごとに `ls-remote` 1回
      （使い回しあり）、証にならない ref があるときだけ `cat-file`・`rev-list` を1回ずつ足す。
    - ワークスペース自身の追跡 ref はこの照合をしない（`main` だけの clone なので実質 `origin/main` だけ。既知の限界）。
  - **reflog にしか無いコミットは数えない**（既知の限界。ワークスペースでもサブモジュールでも）。`--reflog` まで数えると、
    `--amend` で書き換えた前のコミットのために 90 日間ワークスペースを残すことになるため。
  - **push 済みかは remote に聞いて確かめる。** session dir は `main` だけを取る clone なので、作業ブランチを
    push しても手元に `origin/<branch>` ができず、手元の ref だけでは「未 push」に見える。だから
    **ほかに残す理由が無い dir だけ**、消す直前に `git ls-remote --heads` で remote のブランチ先端を取り、
    その先端（とそこから辿れるコミット）に含まれるものは push 済みとして数えない。照合が失敗・タイムアウト
    （20 秒）したら**残す**（INFO に `(ls-remote failed; …)` と出る）。同じ remote への問い合わせは 60 秒
    使い回すので、スイープ 1 回でネットワークを叩くのは remote ごとにほぼ 1 回
  - squash マージ後に remote ブランチが消された作業ブランチは、先端がどの head とも一致しないので**残す**。
    patch-id などで「マージ済みらしい」と推測して消す側に倒すことはしない
- **git が無視するファイル** — `.gitignore` / `.git/info/exclude` に当たるもの。`git status --ignored=matching`
  で `!!` として拾い、次のものだけを**作業に数えない**。それ以外（`.env`、`AUDIT.md`、無視された
  `notes/` の中身など）は作業として残す:

| パスのどこかに次のディレクトリ名を含む | `node_modules` `bower_components` `.venv` `venv` `vendor` `.eggs` `__pycache__` `.pytest_cache` `.ruff_cache` `.mypy_cache` `.tox` `.nox` `.cache` `.gradle` `.dart_tool` `.parcel-cache` `.turbo` `.terraform` `build` `dist` `target` `.build` `.next` `.nuxt` `.svelte-kit` `.angular` `.expo` `.godot` `build_web` `coverage` `htmlcov` | パッケージマネージャ・キャッシュ・ビルド出力。ツールが作り直せる |

**線引きの理由**: 再生成できるものまで「作業」に数えると、スイープがほぼ効かなくなる（#749 の 118 GB の再来）。
本番実測（2026-10-28、git 管理下 192 件）では無視ファイルを持つものが 185 件あり、その大半が上の表のもの
だった。表に無いものは**残す**側。無視されたディレクトリが `dir/` の1行で返ってきたときは中を開いて
ファイルごとに同じ規則で判定する（2000 ファイルを超えたら作業とみなす）— リポジトリが `.claude/` を丸ごと
無視していても、c-lord の SKILL.md だけなら消え、利用者自身の skill があれば残る。

**無視されたディレクトリの中に clone したリポジトリは作り直せない**（#1241。以前は `vendor/` などを丸ごと読み飛ばし、
そこに clone したリポジトリのローカルにしか無いコミットをワークスペースごと消していた）。上の規則で作業に数えなかった
無視ディレクトリ（`vendor/`・`node_modules/` など作り直せるものを含む）は、そのディレクトリ自身と、その下2段まで
（`vendor/lib`・`vendor/<org>/<pkg>`・`node_modules/@scope/pkg`）に `.git` があるかを見る。あれば、入れ子のリポジトリと同じく
stash・push していないコミット・その中のサブモジュールを数え、加えてそのリポジトリ自身の `git status`（untracked を含む）に
何か出れば `vendor/lib: uncommitted changes` として残す。その `git status` は無視ファイルも見る（`--ignored=matching`）。
そのリポジトリが無視している `.env` なども、どの commit にも無いので作業に数える。作り直せるもの（上の表）だけは数えない。理由は `vendor/lib: 1 unpushed commit(s)` のようにパス付きで出す。
読めないディレクトリは `vendor: nested repos unknown (unreadable)` として残す。シンボリックリンクは辿らない（消すときも
リンク先には届かない）。2段より深いところは見ない（既知の限界。毎回の掃除で `node_modules` を全部歩くのは、作り直せるものの
一覧があることの意味を無くす）。見つかったリポジトリの中のサブモジュールが持つ無視ディレクトリ・その中にさらに clone した
リポジトリも見ない（既知の限界）。無視されたディレクトリの中の、作り直せる名前のディレクトリより下（`tmp/x/build/lib` のように
3段目以降）に clone したリポジトリも見つからず、ファイルの判定でも `build/` ごと作業に数えないので消える（既知の限界。main から
前からある）。git の呼び出しは、見つかったリポジトリ1つにつき `rev-parse`・`rev-list`・`ls-files`・`status` の4回。
**最初に「残す」理由が見つかった時点で探すのをやめる**（W57 の12回目のレビュー。以前は見つけた後も残りのリポジトリを1つずつ
調べ、遅いリポジトリ（フィルタが止まるなど）が N 個あると打ち切りの待ちが N 回積み重なった）。見なかった分は
`vendor: …and more not checked` と書く。ほかの理由（利用者の変更・stash・push していないコミット・サブモジュール）ですでに
残すと決まっているときは、無視ディレクトリの中は探さない。そのときも探さなかったディレクトリを
`…and more not checked: vendor/, build/ (+2 more)` と書く（W57 の13回目のレビュー。書かないと、`/workspace-cleanup` の dry run が
途中までの理由をすべての理由のように見せていた）。
**無視されたディレクトリの中の bare リポジトリ**（`build/x.git` のような push 先・ミラー。`HEAD`・`objects/`・`refs/` を持つ）も、
ref を1つでも持っていれば `build/x.git: bare repository (holds refs)` として残す（ワークスペースと一緒に消えるため）。git の
呼び出しは1つにつき `for-each-ref` 1回。同じ2段までしか探さないので、それより深い bare リポジトリは「ワークスペースの中の
remote は証にしない」（上）だけが守る。

session cleanup: keeping /…/1559120173389062204 — 1 unpushed commit(s) on no remote branch (ls-remote failed; pushed branches could not be checked) (thread=…)

**`/workspace-cleanup` も残した理由を同じ言い方で出す**（#1016）。Discord の「⚠️ Dirty — not removed」欄の
各行は `` `<パス>` — 2 unpushed commit(s) on no remote branch `` / `` `<パス>` — uncommitted user work: !! .env `` の形で、
dry run の「Would skip」欄も同じ理由を出す。stash は push していないコミットとは別に `1 stash entry` と書く（#1045。以前は stash のコミットが `2 unpushed commit(s)` と数えられていた）。`refs/stash` が在れば、reflog が空でも（`git reflog expire` の後や `update-ref` で置いた stash）最低1件と数えて残す（#1080。以前は 0 件と数えてフォルダごと stash を消していた）。**サブモジュールの中の stash も数える**（#1121）。サブモジュールの stash は `<ワークスペース>/.git/modules/<名前>` にあってフォルダと一緒に消えるのに、親の `git status` にも `refs/stash` にも出ないため、以前は clean と読んで stash ごと消していた。理由は `sub: 1 stash entry` のようにサブモジュールのパス付きで出す（入れ子は3段まで）。`.gitmodules` に載っていない、`git add` しただけの入れ子のリポジトリ（gitlink）の stash も同じように数える（#1207。以前は `.gitmodules` が無いと見に行かず、stash ごと消していた）。**チェックアウトの無いサブモジュールも見る**（#1181）: `git submodule deinit` や `git rm` の後はフォルダに `.git` が無くなるが、stash は `.git/modules/<名前>` に残っていてフォルダと一緒に消える。そこで `.git/modules` の下の git ディレクトリのうちチェックアウトに対応しないものも確かめ、モジュール名付きで理由に出す（以前はチェックアウトされているものだけを見ていて、stash ごと消していた）。**サブモジュールの中の、push していないコミットも数える**（#1198）。チェックアウトされているサブモジュール・`.gitmodules` の無い入れ子のリポジトリ・チェックアウトの無い `.git/modules` の git ディレクトリのどれでも、**手元のすべての ref**（ブランチ・タグ・notes・`refs/original`・`refs/keep/*` などと HEAD。`git rev-list --all`。stash は別に数えるので除く）と、リンクされた worktree の detached HEAD・その worktree だけの ref（`refs/worktree/*`・`refs/bisect/*`。`--all` は git 2.43 では他の worktree のこれらを見ないのでファイルから読む）から辿れて、remote ブランチ（`refs/remotes/*`）から辿れないコミットがあれば残す理由に数え、`sub: 1 unpushed commit(s)` と出す。チェックアウトされていても親の `git status` には出ない場合がある（HEAD を記録済みのコミットに戻したがブランチにコミットが残っている／親がサブモジュールの新しいコミットを記録して push した）ため、以前は deinit / `git rm` の後でもチェックアウト中でも、そのコミットをフォルダごと消していた。remote の無い入れ子のリポジトリは、すべてのコミットがそこにしか無いので残す。**タグ（`refs/tags/*`）は「載っている」証にしない**。タグは消す対象の `.git/modules/<名前>` の中にあり、手元では fetch したタグと手で打った `git tag wip` を見分けられないため（タグを証にしていたときは、タグを打った detached のコミットを唯一のコピーごと消していた）。

### スリープだけの例外

### 復元したときに言うこと — 「起こさない」と決めた側の責任 (#730)

**停止から戻したとき、docker は自動で起こさない。** compose の起動は数十秒〜数分
かかることがあり、「履歴を読み返したいだけ」の復帰で重い処理を走らせるのは筋が悪い
（#540 の確定事項）。

**その代わり、止まったままであることを1行だけ言う。** これは親切ではなく、
「起こさない」と決めたこと自体の責任。止めたときは
「開発環境 (docker) ⏹ 停止（:55322 を解放）」と**はっきり言う**のに、戻したときに
黙っていると、利用者は「▶️ 再開しました」だけを見て**環境も戻ったと思う**。
気づくのは10分後の connection refused で、そのとき原因は c-lord に見えない。

```
▶️ このスレッドのワークスペースを再開しました
🏷️ スレッド名: W3 │ #730 メモリ設計
💬 このスレッドにメッセージを送ると、これまでの会話の続きから再開します。
⏹ 開発環境 (docker) は停止したままです（`supabase_db_555`）。自動では起こしません — 必要なら Claude に「開発環境を起動して」と頼んでください。
```

| いつ | 出すか |
|---|---|
| `/workspace-start`（旧 `/reopen-workspace`） | **出す** |
| 停止中スレッドへの投稿による自動復帰（#700） | **出す** |
| 「▶️ 再開する」ボタン（#512） | **出す** |
| **スリープからの復帰** | **出さない**（docker を止めていないので、言うことが無い） |
| コンテナが1つも無い | **出さない**（持っていない物の説明を増やさない） |
| docker が無い / 落ちている | **出さない**（例外も出さない。docker は依存ではない） |

**文面は1つの関数**（`workspace_notice.restored_devenv_line`）から作る。復元経路は
`/workspace-start` と `_reopen_thread`（投稿・ボタン）の2つあり、2本書けば必ずズレる
— #538 がまさにそれだった。

一部だけ動いている（db は上がっているが studio は落ちている）ときは、**止まっている
方だけ**を挙げる。利用者が自力で一番推測しにくい状態なので。

「止まっている」の判定は停止・スリープの通知と同じ（`holds_ports`、#1182）。`paused`・
`restarting` のコンテナはポートを握ったままなので、ここには挙げない（#1221）。以前は
`running` かどうかで判定しており、停止の通知で「▶️ 動いたまま」と書いた同じコンテナを、
戻したときには「停止したまま」と書いていた。
