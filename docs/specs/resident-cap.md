# あるべき動き: 常駐ワークスペース数の上限

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

決定の経緯は #540 / #576。スリープそのものは [`workspace-sleep.md`](workspace-sleep.md)。

## これは何か

**同時に claude を抱えていられるワークスペースの本数に上限がある。** 超えたら、
**いちばん長く使われていないもの**から自動でスリープします（#572 の仕組みをそのまま使う）。

| | |
|---|---|
| 既定の上限 | **`MemTotal` から自動算出**（`CLORD_MAX_RESIDENT_WORKSPACES` で上書き、`0` で無効） |
| 超えたとき | いちばん長く使われていないものからスリープ |
| **新規の作成** | **絶対に待たされない** |
| 走っているターン | **絶対に選ばれない** |
| 戻し方 | 投稿するだけ（無言復元） |
| 緊急ブレーキ | `MemAvailable` が総量の10%を3回連続（90秒）下回ったら、TTL を待たずにスリープ |

## これは主たる制御ではない

**主たる制御は TTL**（[スリープ4時間](workspace-sleep.md) / 停止7日）。上限は
**暴走時のバックストップ**で、平常時は一度も発火しないのが正常です。

実測（tachikoma 31.34 GiB）では TTL=4h の p95 常駐は13本、自動算出の上限は27本なので、
**通常運転で上限に触ることはありません**。触るのは「TTL が想定していない速さで
増えた」異常時だけ。

## `MAX_CONCURRENT_SESSIONS` はこの上限ではない

**名前が紛らわしいので明記します。**

| 設定 | 何の上限か | 何を止めるか |
|---|---|---|
| `MAX_CONCURRENT_SESSIONS` | **同時に走るターン数** | ターンの実行。終われば即解放される |
| `CLORD_MAX_RESIDENT_WORKSPACES` | **常駐する claude の本数** | tmux に居座る claude プロセス |

`MAX_CONCURRENT_SESSIONS` のセマフォは `async with self._semaphore:` が**ターンの実行だけ**を
包みます。ターンが終わればセマフォは解放されますが、**tmux の claude は生き続けます**。
つまりこれは「常駐プロセス数の上限」を一度も縛ったことがありません。本番で 30 に
設定されているのを「30本までしか常駐しない」と読むのは誤りです。

## 既定値だけは TTL と扱いが違う

#540 の整理:

| パラメータ | ホスト規模に依存するか | 既定値の決め方 |
|---|---|---|
| アイドル TTL（4時間 / 7日 / 30日） | **しない**（人間の復帰間隔で決まる） | 全ホスト共通の定数 |
| **常駐上限 N** | **する** | **`MemTotal` から起動時に自動算出** |

```
N = max(2, floor(MemTotal_GiB × 0.4 / 0.45 GiB))
```

| ホスト RAM | N |
|---:|---:|
| 2 GiB | 2（下限。小規模ホストでは上限が主制御になる） |
| 8 GiB | 7 |
| 16 GiB | 14 |
| 31.34 GiB（tachikoma 現在） | 27 |
| 47 GiB | 41 |

- **0.45 GiB** = claude 1本の実測限界コスト（PSS private 255–398 MB ＋ 残骸ウィンドウ分）
- **0.4** = 「c-lord の常駐分がホスト RAM の4割を超えたら、c-lord 専用機でない限り事故」という保守側の線。実測ホストには naranu 3.8GB / factorio 3.0GB / java 2.6GB が同居している

**固定既定値を配ってはいけません。** 2 GiB の VPS に「30」を配ると、その人のホストが死にます。

### cgroup があればそちらが勝つ

コンテナの中では `/proc/meminfo` の `MemTotal` は**ホスト全体**を指します。
2 GiB を割り当てたコンテナで 47 GiB を読むと上限は41になり、**制限のあるほうの環境で
確実に OOM します**。だから読む順番は:

1. `/sys/fs/cgroup/memory.max`（cgroup v2）
2. `/sys/fs/cgroup/memory/memory.limit_in_bytes`（cgroup v1）
3. `/proc/meminfo` の `MemTotal`

v2 の `max` と v1 の巨大なセンチネル（2^63 近辺）は「無制限」なので、素直に整数として
読まずに次へ落とします。`MemAvailable` 側も**同じ出所**から取ります（cgroup の総量と
ホストの空きを比べても比率になりません）。

### `/proc` の無い OS（macOS, #899）

`/proc/meminfo` が無いときは、総量を `sysconf`（`SC_PHYS_PAGES × SC_PAGE_SIZE` = 搭載メモリ）、
空きを `sysctl kern.memorystatus_level`（カーネルが「使える」とみなす割合 % — アクティビティモニタの
メモリプレッシャーの元の数字）× 総量から取ります。以前は総量が 0 と読まれ、**どんな Mac でも上限が
最小値の 2 に固定**されていました。

**空きが読めないときは緊急ブレーキを止めます**（踏まない）。総量だけ本物で空きが 0 だと
「メモリが尽きている」に見え、アイドルのワークスペースを毎回眠らせてしまうからです。
Linux の読み方（上の 1〜3）は変わりません。

## 超過時の挙動: LRU でスリープ。新規は待たせない

**待たせるのは却下です。** 実測で yousan は同時に11本の並行タスクを走らせています。
待ちキューを入れると、**いま普通にできている並行作業が塞がれます**。

> 上限を主制御にすると「他人の作業を殺す」か「自分の作業が始まらない」の
> **どちらかが必ず起きる**。

c-lord は前者を選び、しかも殺す先を「**いちばん長く使われていないもの**」に限定します。
復帰は投稿1通（無言復元）なので、外したときの損害は次のターンが数秒遅いことだけです。

### 「いちばん長く使われていない」は何の時刻で測るか（#1142）

**最後の依頼（`last_used_at`）と、Claude が transcript（サブエージェントのものを含む）に
最後に書いたイベントの時刻の、遅いほう**で並べます。idle-sleep（#922 / #964）と同じ時計です。
上限の超過時も緊急ブレーキも、この順番で古いものから選びます。

`last_used_at` だけで並べていたときは、依頼のあと何時間も自分で作業を続けているスレッド
（バックグラウンドの待ち・起床予定・サブエージェント）ほど「長く使われていない」に見え、
2026-10-29 23:31 のブレーキは **17 秒前まで画像を作っていたスレッド**を、1.6 時間静かだった
スレッドより先に眠らせました。transcript が無い・読めないワークスペースは、従来どおり
最後の依頼の時刻で並びます。

### 眠らせるのは「眠らせる直前の超過分」だけ（#1094）

数えてから眠らせるまでのあいだに `claude` が自分で終わって窓が消えた候補は、**自分で常駐から
外れた**ので超過分から引きます。眠らせ損ねた（窓が残ったまま失敗した）ときだけ、次の候補で補います。
以前は窓の消えた分まで補い、上限 2 で 1 本しか残らないことがありました。
「窓が消えた」と読むのは、眠らせる処理が**殺す窓が無かった**と答えたときだけです（#1192）。
`kill-window` が失敗した・tmux のマネージャが引けなかったなど、窓が残っているかもしれない失敗は次の候補で補います。ただし kill が失敗と返ったあとは、「答えが無い」を区別できる聞き方で聞き直します（#1219）: tmux が**答えて**「その窓はホストのどこにも無い」と言えば消えた側に数え（超過分から引く）、窓がまだあると**答えた**なら補う側に数えます。聞き直しにも答えが無い（時間切れ — tmux が詰まり続けている）ときは、**1 回の tick で 1 本までは補い、2 本目でその tick を終えます**（次の tick で数え直す。WARNING は間引いて出す）。時間切れの kill もあとで実行されうるので、補い続けると詰まりが続く間に全部を眠らせます。かといって 1 本目で止めると、kill が通らない最古の窓が毎回先頭に来て、その後ろを誰も眠らせず上限を超えたままになります。同じ理由で、聞き直しに答えが無かった窓は**順番の最後**に回し、眠らせるか聞き直しに答えが返るか常駐から外れるまでそのままにします（kill が通らない古い窓が何本あっても、その後ろが試される）。以前は聞き直さずに全部を補う側に数えていたため、tmux が遅くて `kill-window` が時間切れになりつつ実際には実行されていると、1 回の tick で超過 1 本に対して常駐 5 本すべてを眠らせていました。
以前は眠らせ損ねた分もすべて「窓が消えた」と数え、最古の窓の kill が失敗し続けると上限を超えたまま止まっていました。

眠らせる前の「窓はあるか」の確認で tmux が答えなかった（`tmux -V`・`show-option`・`list-windows`
の時間切れ）ときも、窓は**残っている**と数えて次の候補で補います（#1206）。以前はこの時間切れを
「窓が無い」と読んで消えた分に数え、tmux が詰まった窓が上限を超えたまま残っていました。
tmux が「サーバが無い」「そのセッションは無い」と答えたときは、窓が無いという答えです。

ただし「窓が無い」と読むのは、**ホスト全体でも**そのスレッドの `claude` が見つからないときだけです
（#1213）。常駐は `list-panes -a`（ホスト全体）で数えますが、眠らせる処理はスレッドのバインドが
**いま**指すセッションの中しか見ません。`/clord-thread-init` でバインドを変えた直後は、窓が次のターンで
移されるまで古いセッションに残っているので、その窓は**残っている**と数えて次の候補で補います
（古いセッションの窓をここから殺すことはしません）。数えるのはこの c-lord の窓（`@clord_owner` が自分か空）だけで、同じ tmux サーバにいる別の c-lord（本番と staging など）の窓は「無い」側です — 数えると、眠らせようのない他人の窓の代わりに自分の生きたワークスペースを眠らせてしまいます。以前は「窓が無い」と読んで消えた分に数え、
上限を超えたまま止まっていました。ホスト全体の一覧が時間切れのときも、残っている側に数えます。

### 絶対に選ばないもの

- **走っているターンを持つワークスペース。** 上限のために動いている作業を殺すのは、上限の意味そのものを裏切る
- **既にスリープしているもの。** 数が収束しなくなる
- **Discord から見えないスレッド**（Forbidden。権限が戻るかもしれない）。tmux の窓が生きていても眠らせようがないので飛ばし、**次に古いものを代わりに眠らせて、1回で上限まで戻します**（#1033。idle_sweep の #593 と同じ形）。引けなかったスレッドはプロセスの間覚えておき、毎回 Discord に聞き直しません
- **Discord から消されたスレッド**（NotFound）は眠らせる代わりに**窓を閉じ**、**常駐数にも数えません**（#1086）。誰も話しかけられない Claude がメモリと枠を持ち続け、消したスレッドが上限本数以上あると、生きているワークスペースが代わりに毎回眠らされていました。閉じるのはこの c-lord の窓（`@clord_owner` が自分か空）だけで、目印の比較と削除は tmux の1コマンド（#1085）。走っているターンがあれば閉じずに待ちます。閉じられなかった窓は次の tick でもう一度閉じにいきます（上限を下回っていても、緊急ブレーキ中でも）
- **`sessions` の行が無いウィンドウ。** アイドル時間が測れないので順番を付けられない。そういう残骸は startup の tmux リーパー（#570）と行なしディレクトリの掃除（#613）の担当

### 「走っている」は何で判定するか（#742）

**bot の再起動を生き延びる根拠で判定します。** 根拠は2つあり、**両方**を見ます:

| 根拠 | 何を知っているか | 再起動すると |
|---|---|---|
| `ClaudeChatCog._active_tasks`（メモリ上） | この bot が始めてまだ待っているターン。ペインがまだ spinner を描いていない立ち上がりも分かる | **空になる** |
| **ペインの working spinner**（`tmux capture-pane`） | Claude Code 自身が描いている実行中表示 | **残る** |

メモリ上の台帳**だけ**を見ていたのが #742 のバグです。tmux の `claude` は bot の再起動を
生き延びる（#503）のに、c-lord だけが「誰も走っていない」と思い込み、**31分走っていた
ターンを緊急ブレーキが眠らせました**（2026-09-14。スレッドには1文字も出ないまま26時間停止）。

`last_used_at` は代わりになりません。**ターンが始まった時刻**しか書かないので、
長く走っているターンほど「長くアイドル」に見え、真っ先に選ばれてしまいます。

**ペインの判定は「括弧の経過タイマー」で行います**（`c_lord/pane_running.py`）:

```
✶ Transfiguring… (4m 6s · ↓ 48.0k tokens)   ← 実行中
✻ Sautéed for 14s · done 9:08 AM            ← 終わっている（括弧が畳まれる）
```

glyph（`✢ ✻ ✶`）の有無では判定しません。**終わったペインにも glyph は残る**ので、
それで数えると待機中のほぼ全部が「走っている」になり、上限が1本も眠らせられなく
なります（ブレーキを無効化したのと同じ）。この判定はスレッドのランプ（🟢/🟡）と
同じ根拠で、定義は1箇所（`pane_shows_running()`）にしか置きません。

**ペインが読めなかったものは「走っている」側に倒します**（#1034）。再起動直後は
メモリ上の台帳が空なので、ペインが唯一の根拠です。`capture-pane` のタイムアウトなどで
読めなかったとき「走っていない」と同じに扱うと、最古の走行中ターンが選ばれます（#742 と
同じ結果）。読めなかったものはその tick では選ばず、次の tick で読み直します。外したときの
損は「1 tick 上限を超えたまま」だけです。`list-panes` 自体が読めなければ候補は全部選びません
（tmux のサーバが無いのは「誰も走っていない」という答えで、読めなかったのではありません）。
「サーバが無い」とみなすのは `no server running` と、ソケットが無い・誰も待っていない
（`error connecting to … (No such file or directory | Connection refused)`）ときだけです。
**`tmux -V` の時間切れや、サーバはあるのに接続を断られた（`Resource temporarily unavailable`）
ときは「読めなかった」**です（#1095）。ホストが詰まっているのはまさにブレーキが働く場面で、
そこで「誰も走っていない」と読むと走っているターンを眠らせてしまいます。
`tmux -V` の時間切れは覚えません（#1193）: 窓を作る側（tmux のマネージャ）も、答えが無かった回は
「tmux が無い」と覚えずに次の回で聞き直します。以前は最初の1回の時間切れを bot の再起動まで
「入っていない」と覚え、一瞬の詰まりでそのチャンネルは窓が作れなくなっていました。

**聞くのは眠らせる直前だけ、対象も「いま選ぼうとしている常駐」だけ**です。1本につき
`capture-pane` 1回かかるので、平常時（上限内・逼迫なし）は1回も呼ばれません。

### 数えるのは「自分のもの」だけ

1台の tmux サーバを、そのホストの c-lord 全部と、人間の手作業が共有しています。
ホスト全体で数えると、**このボットが決して眠らせられない他人のワークスペース**
（victim は自分の `sessions` 行からしか選ばれない）が、自分の利用者を押し出すことに
なります。だから常駐数は **`sessions` に行があるものだけ**を数えます。

ホスト全体の逼迫は**緊急ブレーキ**の担当です（`MemAvailable` を見るので、そもそも
ホスト全体が対象）。上限は自分が責任を持てる範囲だけを見る、という役割分担です。

### 「待たせない」は構造で担保する

**ワークスペースを作る経路（`claude_chat` / `_run_helper` / `tmux` / `session_dir`）は、
上限のシンボルを1つも参照しません。** 参照が無ければ「待つコード」は書きようがない。
`tests/test_resident_cap.py::TestNewWorkspacesAreNeverBlocked` が AST で参照を検査して
これを固定します。実装者の善意ではなく形で守る、という #570 / #612 と同じやり方です。

## 緊急ブレーキ

`MemAvailable` が総量の **10%** を **3回連続**（30秒ごとのサンプル = 90秒）下回ったら、
TTL を待たずにアイドルの長い順にスリープさせ、**回復したら止めます**。1本ずつ眠らせて
毎回メモリを読み直す — 目的はスパイクを消す最小の介入であって、一掃ではありません。

**発火は WARNING 以上でログに大きく残します**（`log_ctx()` 付き。「なぜ自分の
ワークスペースが眠ったのか」を後から辿れるように）。

### 1本も眠らせられないときは、黙る（#742）

走っているものを守る以上、**「全部走っていて1本も眠らせられない」は正常な状態**です。
このときブレーキは何もせず 0 本を返します（無限ループにはなりません）。

ログは **1 episode（踏んでから戻るまで）につき1回**だけ出します。30秒ごとに
「ENGAGED」「眠らせられるものが無い」を出し続けると、**逼迫時にいちばん読みたい
ログを自分のノイズで埋める**ためです（#678 と同じ失敗を、いちばん悪い場所でやること
になる）。黙らせた分は次の1行が `(+N suppressed in the last Ms)` で数を持ちます。
回復して再び踏んだら、それは別の episode なので必ずまた出します。

### 上げる方向には決して動かない

**「余裕があるから上限を上げる」は絶対にやりません。** 上げる方向は事故を増やすだけで、
利用者から見た挙動が予測不能になります。連続フィードバックループ（`MemAvailable` を
常時見て上限を動かす）も却下: **非決定的でテストできず、「なぜ自分のワークスペースだけ
落ちたのか」が説明不能になります**。

これも構造で担保します — `ResidentCapLoop.limit` は**読み取り専用のプロパティ**で、
セッターがありません。書ける属性なら、いつか誰かが「余裕があるから広げよう」と
書けてしまう。書けない値なら、上げる方向のコードは**書けません**。

### なぜ「常時フィードバック」ではなく「スパイクだけ」なのか

緊急事態は実在します（起動5日で PSI メモリ full ストール 2763秒 / スワップアウト累計
27 GB）。しかし PSI の avg10 は 0.00 で、**常時逼迫ではなく間欠**です。だから常時
フィードバックは過剰で、スパイクだけ潰すブレーキが正解になります。

## 通知の文言

上限で眠らせたものは4時間経っているとは限りません。10分前に使ったワークスペースを
「4時間 操作が無かったため」と説明したら**嘘**になります。通知は理由ごとに説明の1行だけが
変わる仕組み（#571）なので、そこを正しく使います:

| 理由 | 説明の1行 |
|---|---|
| `IDLE` | 💤 **4時間 操作が無かったためスリープしました。** |
| `CAP` | 💤 **常駐ワークスペースが上限（30本）に達したため、いちばん長く使われていないものからスリープしました。** |
| `PRESSURE` | 💤 **ホストのメモリが逼迫したため、いちばん長く使われていないものからスリープしました。** |

**棚卸しの中身（Claude / 開発環境 / 作業フォルダ / 会話履歴 / volume）は3つとも完全に同一です。**

なお通常のスリープ同様、**この通知が出るのは docker が動いていたときだけ**です
（[workspace-sleep.md](workspace-sleep.md) の「唯一の例外」）。

## 常駐数の数え方

`tmux list-panes -a` **1回**で、`@thread_id` を持ち、かつペインが claude を走らせている
ウィンドウを数えます。セッションごとに歩くと（`list-windows` ＋ `list-panes` ×N）
本番規模で40プロセス起動になり、30秒ごとには重すぎます。

**claude だと積極的に判定できたものだけ**を数えます。前景がシェルのペインはウィンドウを
持っているだけで、上限が対象にしている ~400 MB は持っていません。数に入れると、
**残骸のために生きたワークスペースを追い出す**ことになります。

**数えるのと「走っているか」を見るのは別の話**です。数えるほうは `list-panes` 1回で
済みますが、走っているかはペインの中身を見る必要があるので、上の
[「走っている」は何で判定するか](#走っているは何で判定するか742) のとおり
**眠らせる直前にだけ**聞きます。

## 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `CLORD_MAX_RESIDENT_WORKSPACES` | `MemTotal` から自動算出 | 常駐上限。`0` で無効 |
| `MAX_CONCURRENT_SESSIONS` | 3 | **別物** — 同時に走るターン数（上記参照） |

起動ログに算出結果が出ます:

```
Resident cap: 27 workspace(s) (memory budget source: 31.3 GiB total)
Started resident-cap loop (limit=27, interval=30s, emergency<10% of total)
```
