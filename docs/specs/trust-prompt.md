# あるべき動き: 作業ディレクトリの信頼ダイアログ

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

スレッドごとの作業ディレクトリは毎回新しく clone されるので、Claude Code はその中で初回に必ず

```
 Quick safety check: Is this a project you created or one you trust? ...

 ❯ 1. Yes, I trust this folder
   2. No, exit

 Enter to confirm · Esc to cancel
```

を出します。これは `--dangerously-skip-permissions` でも回避できません。c-lord がこれを**自動で承認**するので、
利用者は普段このダイアログを見ません。

## あるべき動き

### 正常時

- ダイアログが出たら、c-lord が「**Yes, I trust this folder**」を選んで閉じる
- 承認は **1つのダイアログにつき 1 回**。閉じたら次のポーリングでは何も送らない
- 利用者から見て、スレッドには何も出ない（普通に Claude が動き出す）

### 「Yes」の位置は版によって違うので、押す前に読む

Claude Code は同じダイアログを 2 つの形で出してきた実績があります。

| 版 | 表示 | カーソル初期位置 |
|---|---|---|
| ≤ 2.1.247 | `❯ 1. Yes, I trust this folder` / `  2. No, exit` | **Yes** |
| ≥ 2.1.248 | `❯ No, exit` / `  Yes, I trust this folder` | **No** |

**どちらでも「Yes」に当たるまで動かしてから確定する**こと。決め打ちで Enter を押すと、後者では
**「No, exit」を選んで claude を終了させます**。

さらに、**カーソルを動かしたつもりになってはいけません**。この TUI はナビゲーションのキーを取りこぼす
ことがあり（#171）、後者の形では取りこぼしがそのまま「No, exit で確定」になります。なので c-lord は

1. `Down` を送る
2. **ペインを読み直して、カーソルが本当に「Yes, I trust this folder」に乗ったかを確かめる**
3. 乗っていれば `Enter`。まだ「No, exit」なら `Down` からやり直す（有限回）

の順で動きます。有限回やっても「No, exit」のままなら、**Enter を送りません** — 送れば claude が死ぬので、
何もしない方がましだからです（そのダイアログは下の「閉じないとき」の経路で中断されます）。

ただしこの見送りは、**カーソルが「No, exit」だと読めたときだけ**です。ペインが読めない（選択肢の行が
1つも解釈できない）ときは従来どおり `Enter` を送ります。「読めないから確定しない」にすると、将来
ダイアログの形が変わっただけで**全スレッドが永久に止まる**ため、直そうとしている不具合より悪くなります。

### 承認したのに claude が居ないときは、**待たずに立て直す**

ダイアログがペインから消えたことは、**claude が生きている証拠にはなりません**。「No, exit」で閉じた場合も
ダイアログは消え（下の「死んだダイアログ」の形になり）、claude は居なくなっています。

なので c-lord は、ダイアログを確定させたあと **claude が実際に走っているかを確かめます**。居なければ

- **その場で claude を起動し直し、同じプロンプトで続きをやり直す**（有限回）
- 回数を使い切ったら、**専用の文言**で中断する:

```
⚠️ 信頼ダイアログの応答に失敗しました
作業ディレクトリを信頼するダイアログ（Yes, I trust this folder）に答えたあと、claude が起動して
いませんでした。起動し直しても同じだったので、このターンは走っていません。
```

- **「応答がありませんでした」「起動に失敗したかクラッシュした可能性があります」とは言わない。**
  どちらも原因を知らない文言で、読んだ人をペイン以外の場所へ探しに行かせるため

### 承認しても閉じないとき — **黙って撃ち続けない**

承認を送っても同じダイアログが出たままなら、c-lord は **数回でやめて、スレッドに理由を出して中断します**。

```
⚠️ 信頼ダイアログが閉じられませんでした
作業ディレクトリを信頼するか確認するダイアログ（Yes, I trust this folder）がペインに出たまま閉じません。
同じ承認を送り続けないよう、c-lord はここで中断しました。

確認すること:
• /clord-attach (または tmux) でペインを開き、ダイアログを手で承認する
• claude が落ちていないか（ペインがシェルに戻っていないか）を見る
• 復旧したらもう一度送る
```

- **「タイムアウトしました」「応答がありませんでした」とは言わない。** 原因が分かっているのに別の場所を
  探させることになるため
- 中断は**数回の試行で**行う。何十回も送らない

### 死んだダイアログは、ダイアログではない

Claude Code は代替画面を使わないので、**`claude` が終了してもダイアログの文字はペインに印字されたまま残ります**
（下にシェルのプロンプトが出る）。これは**もう押せる相手ではない**ので、c-lord は承認を送りません。

判定は「確認フッタ（`Enter to confirm …`）より下に、空行以外があるかどうか」で行います。生きているダイアログは
全画面モーダルなのでフッタが最後の行になり、死んだ残骸にはその下にシェルのプロンプトが出るためです。
（ダイアログを起動したコマンド行は**上**に残るので、「シェルのプロンプトがどこかにあるか」では判定できません。）

## バグの例

- 承認を毎秒送り続ける（**#630 の症状: 2分20秒で178回**）。しかも死んだシェルに Enter を撃つとシェルが新しい
  プロンプトを印字する＝ペインが変化するので、**無活動タイムアウトも発火しない**。ダイアログが画面上端から
  流れ落ちて初めて止まり、そこから idle timeout で「応答がありませんでした」になる（発注は丸ごと消える）
- 承認のつもりで「No, exit」を選び、claude を終了させる
- 閉じないダイアログについて何も言わず、タイムアウトとして報告する
- **ダイアログに答えたあと claude が居ないのに、居るものとして 120 秒待ち、
  「起動に失敗したかクラッシュした可能性があります」で終わる**（#684 の症状:
  発注が丸ごと消え、誰も気づかないまま数日放置された）
