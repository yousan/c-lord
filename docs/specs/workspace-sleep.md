# あるべき動き: スリープ（4時間で claude だけ止める）

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

決定の経緯は #540、実装は #572。用語と3操作の全体像は [`workspace-vocabulary.md`](workspace-vocabulary.md)。

## これは何か

**4時間 誰も触らなかったワークスペースは、claude プロセスだけが静かに止まります。**
次にそのスレッドに投稿すれば、**何も聞かれず・何も告げられず**、会話の続きから再開します。

利用者がやることは何もありません。**気づかないのが正常**です。

| | |
|---|---|
| いつ | 最後の**人間の発言**から4時間（`CLORD_IDLE_SLEEP_HOURS`、既定 4） |
| 何が止まるか | **claude プロセスと tmux ウィンドウだけ** |
| 何が残るか | docker・作業ディレクトリ・会話履歴・DBのデータ(volume)・`sessions` の行・スレッド名 |
| 戻し方 | **投稿するだけ**（無言で復元） |
| 手動コマンド | **無い**（下記） |
| 通知 | **無し**。ただし docker が動いていたときだけ1回出す（下記） |

## なぜ要るか

**常駐 claude はターンが終わっても居座り続ける。** リークではなく「片付けないだけ」です
（本番実測: 80時間経過した9本の RSS ドリフトは 0.0〜+7.5 MB/h でほぼ完全にフラット）。
だから TTL で回収すれば確実に効きます。

実トランスクリプト272スレッドを直近14日・15分刻みで再現した常駐数:

| TTL | p95 常駐 | p95 RAM |
|---:|---:|---:|
| **4h** | **13** | **5.2 GB** |
| 24h | 46 | 18.4 GB |
| **なし（#572 以前）** | **249** | **99.6 GB** |

31〜47 GiB のホストが p95 99.6 GB を支えられるはずがありません。いま落ちていないのは
claude が勝手に死んでいるから (#570) であって、設計が支えているからではない。

**なぜ4時間か**: 人間が同じスレッドに戻ってくるまでの間隔の実測 (n=2650) は p95 = 2.42h。
4時間なら**影響を受ける復帰は 3.89%**（26回に1回）で、その1回も無言で復元されるので
利用者からは見えません。

## 守ること

### docker は止めない

スリープは **claude だけ**を止めます。docker は動いたままにします。

- 走っているビルドや DB がスリープで飛んではいけない
- 回収したい 400MB は **claude 側**のもので、docker を止めても増えない

docker まで止めるのは1つ上の操作（**停止** = `/workspace-stop` / 7日自動）の役目です。

### 手動コマンドは作らない

`/workspace-sleep` のようなコマンドは**作りません**。

スリープのゴールは「気づかれないこと」です。手で打てるようにすると
「**停止とどう違うのか**」という説明の要る概念が1つ増え、しかもその説明は
利用者にとって何の得にもなりません。利用者が名前で呼ぶ必要があるのは
**停止**と**削除**の2つだけです。

（内部的には #576 の常駐上限が同じ操作を LRU で呼びます。呼び口は
`SessionManageCog._sleep_workspace_impl` の1つだけで、2つ目の実装は作りません。）

### スレッド名を変えない・マーカーも付けない

`[停止]` のような印は付けません。左のスレッド一覧の見た目は1ミリも変わりません。
印が付く＝利用者が知るべき状態、という約束を守るためです。スリープは知る必要がない。

### 走っているターンには絶対に触らない

`last_used_at` はターンの**開始**時刻なので、5時間走り続けているターンは
タイムスタンプ上アイドルに見えます。殺せば実作業が飛びます。だから
**「ターンが走っていないこと」も併せて見ます**（`ClaudeChatCog._active_tasks`）。

### アイドル判定に tmux の `window_activity` を使わない

Claude の TUI はスピナーとステータス行を描き続けるので、**誰も触っていなくても
更新され続けます**。本番実測では生きている 51 本すべてが「直近1〜3時間以内に
activity あり」に見えました。正直な時計は**最後の人間の発言**（`sessions.last_used_at`）だけです。

## 唯一の例外: docker が動いていたら1行残す

スリープは docker を止めないので、**ホストのポートを掴んだまま**になります。
これは利用者が自力で気づけず、しかも次に環境を立てるとき衝突として跳ね返ってきます
（supabase 実測で1スレッド5ポート占有）。**「知らないと困る」唯一の情報**なので、
このときだけ通知を出します。

通知は他のライフサイクル通知と同じ「**棚卸し**」で、`c_lord/workspace_notice.py` の
1つの関数が組み立てます（手動/自動で別々の文面を書かない — #571）:

```
💤 このスレッドのワークスペースをスリープしました
💤 4時間 操作が無かったためスリープしました。
このスレッドに投稿すれば、そのまま続きから再開します。

   Claude              ⏹ 停止
   開発環境 (docker)    ▶️ 動いたまま
   作業フォルダ          ✅ そのまま
   会話履歴             ✅ そのまま（Claude Code の保持期間 30 日まで）
   DBのデータ (volume)   ✅ そのまま

   ⚠️ 掴んだままのポート
   `supabase_db_...` :55322 / `supabase_studio_...` :55323
```

**動いているコンテナが1つも無ければ、何も出しません。** 終了済みコンテナはポートを
掴んでいないので、例外が存在する理由そのものが無いからです。

## 復元

次にそのスレッドへ投稿すると、既存の `--continue` 復元経路 (#270) がそのまま走ります。
スリープが変えるのは**文言だけ**です:

| 状況 | 投稿したとき出るもの |
|---|---|
| スリープしていた | **何も出ない**（無言で続きから再開） |
| ペインが落ちていた (#464) | 🔄 前回のワークスペースが落ちていたので、会話を復元して続けます。 |
| 停止から「▶️ 再開する」を押した (#512) | 🔄 停止していたワークスペースを復元して、続きから再開します。 |

3つとも「セッションはディスクにあるがペインが死んでいる」という**同じ状態**から
分岐するので、判断は `c_lord/session_resume.py` の `resume_notice()` **1箇所**に置きます。
呼び出し側で分岐させると必ずズレます（それが #538 の事故形）。

**ダイアログもボタンも出しません。** 「復元しますか?」を聞くのは、利用者が頼んでいない
片付けの尻拭いを利用者にさせることです。

### 投稿以外で復元するもの: `/tmux-screenshot` (#642)

**`/tmux-screenshot` は、スリープ中のスレッドでは復元してから撮ります。**

理由は #572 自身が作った副作用です。スリープが入る前、「tmux ウィンドウが無い」は
クラッシュ・手動停止・7日放置という**稀な事故**でした。いまは**4時間触らなければ必ずそうなる**ので、
「メッセージを送れば復元します」という案内文が `/tmux-screenshot` の**通常の返答**になり、
コマンドが画像を返さなくなっていました。

- **復元してよいのは「メッセージを送れば動くスレッド」だけ** — `sessions` 行があり `closed_at` が無い状態
  (`ThreadResume.RESUMES`)。`[終了]` は**利用者自身が選んだ状態**なので、撮影のために勝手に覆しません。
  記録の無いスレッドは復元する対象がありません。どちらも従来どおり案内文を返します
- **ターンは走らせません**。`claude --continue` を**プロンプト無し**で起動し、TUI が入力欄まで来たら撮ります
  (`TmuxClaudeRunner.wake()`)。ここでプロンプトを渡すと、誰も頼んでいないターンが走ります
- **起動条件はメッセージ経路と同じ**（model / effort / `--dangerously-skip-permissions` /
  `--continue` 失敗時は fresh へフォールバック）。組み立ては `ClaudeChatCog.wake_workspace()` に置き、
  ターンの spawn と同じ場所から作ります。別の場所に2つ目の組み立てを書くと、
  起動した claude と次のメッセージが期待する claude が食い違い、1つのチェックアウトに2つ立ちます
- **無言では復元しません**。スリープ自体は無言が仕様ですが、これは利用者がコマンドを打って数秒待たされる場面なので、
  画像に `-# 🔄 停止していたワークスペースを復元してから撮影しました。` を添えます
- **復元したら `last_used_at` を更新します** (`SessionRepository.touch()`)。
  アイドル掃除は「その `last_used_at` で既に処理したスレッド」を飛ばすので、
  更新しないと**撮影しただけのワークスペースが二度と掃除されず常駐し続けます**（機能の顔をしたメモリリーク）
- 復元に失敗したら黙らず失敗を返します（上の「失敗したときは黙らない」と同じ規律）

**`/resync` は対象外です。** あちらは「Discord ミラーの繋ぎ直し」が主目的で、
ペイン PNG はついでに出しているだけなので、復元まで行うかは別の判断が要ります。

### 失敗したときは黙らない

復元に失敗したら（tmux ペインが立ち上がらない等）**エラーを出します**。利用者は何も
操作していないのに c-lord が勝手に畳んだのだから、そこで無言で捨てるのは
「案内どおりにしたのに無反応」(#538) より理不尽です。エラーには**次の手**
（`/restart-claude` してもう一度送る）まで書きます。

## 状態をどこに持つか

`sessions.slept_at` に記録します。**これは文言を選ぶためだけに読みます。**
復元するかどうかは今までどおり「ペインが生きているか」だけで決めるので、
この列が古くても何かを壊すことはありません（`closed_reason` と同じ規律）。

ターンが1回でも走れば `SessionRepository.save()` が `slept_at` を NULL に戻します。
呼び出し側で消し忘れる余地を作らないためで、**この列は「クリアされる」ことしか
起きない**ので `set_slept` と食い違えません。

## 3操作の中での位置

**スリープ ⊂ 停止 ⊂ 削除**。上の操作は下を全部含みます。

| | 操作 | 何をするか | 手動 | 自動 | 逆操作 |
|---|---|---|---|---|---|
| 1 | **スリープ** | claude を止める | なし | 4時間 無操作 | 投稿するだけ（無言復元） |
| 2 | **停止** | スリープ ＋ docker も止める | `/workspace-stop` | 7日 無操作 | `/workspace-start` |
| 3 | **削除** | 停止 ＋ 作業ディレクトリも消す | `/workspace-delete` | 30日 かつ worktree クリーン | 投稿で再 clone |

4時間で眠り、7日で停止し、30日で消える、が既定の一本道です。停止は
`closed_at` を立てるので、**停止済みのものはもうスリープの対象になりません**
（止める claude が居ないので、触れば通知が湧くだけ）。

## 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `CLORD_IDLE_SLEEP_HOURS` | `4` | スリープまでの時間。小数可（`0.5` = 30分）。`0` でスリープを無効化 |

既定値はホスト規模から**算出しません**。この数字は「人がどう Discord を使うか」を
表していて、RAM の量では変わらないからです。2 GiB の VPS でも 47 GiB のホストでも同じ4時間。
