# あるべき動き: Discord と切れていた間に届いたメッセージ

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

c-lord は Discord から 1 本の接続（gateway）でメッセージを受け取っています。ホストの回線や
DNS が落ちるとこの接続が切れ、**切れている間に送られたメッセージは c-lord に届きません**。
Discord 側は投稿を受け付けているので、送った人からは普通に送れたように見えます。

接続が戻ったとき、Discord が「切れていた間の分」を送り直してくれるのは、切断が短く
セッションを再開（RESUME）できた場合だけです。長く切れていてログインし直した（IDENTIFY）
場合は、**切れていた間のメッセージは二度と届きません**。#745 までは c-lord もそれを
取りに行かなかったので、その投稿にはリアクションも返事もログも付かず、ただ消えていました
（2026-09-16、6時間35分の切断中に送られた依頼が、4時間半後に一字一句同じ文面で
送り直されるまで放置された）。

この spec が決めるのは、**接続が戻ったときに、切れていた間の投稿をどう拾うか**です。

## あるべき動き（利用者から見て）

### 正常時

- **切れていた間に c-lord のスレッドへ送った依頼は、接続が戻った時点で実行される。**
  送り直す必要はない。実行のされ方は、その場で届いていた場合と同じ（リアクション 🟢→🟡、
  返事、ワークスペースの復元など）。
- **そのスレッドには、遅れた理由が 1 行だけ出る。**
  `-# 🔌 05:16〜11:52 の間 Discord と接続できておらず、この依頼を受け取れていませんでした。いまから処理します。`
  取りこぼしが無かったスレッドには何も出ない。
- **同じスレッドに何通も送っていたら、1 回のターンでまとめて実行される。** 1 通ずつ流すと、
  後の 1 通が前の 1 通を割り込みで止めてしまい（⚡）、前の依頼が Claude に届かないため。
  Claude には古い順に全部が並んで渡る。1 行の案内も「この間に届いた N 件の依頼を…
  まとめていまから処理します。」になる。
- **ログに残る**（INFO。DEBUG に落とさない — #678）。切断に気づいた時刻、戻った時刻、
  どこから読み直したか、何件拾ったかが、次の形で grep できる:
  - `Discord gateway disconnected at …`（切断の始まり。再接続の失敗が何十回続いても 1 行）
  - `Discord gateway back (ready|resumed) at … — down since … (6h35m45s) …`
  - `[thread=<id>] picked up N message(s) posted while the gateway was down …`
  - `Gateway outage … → … : picked up N message(s) in M thread(s) …`（まとめの 1 行。0 件でも出る）

### 二重に実行しない

**拾い直したメッセージが 2 回実行されることはない。** 次のどれでも 1 回きり:

- **切断の直前に届いていたメッセージ**は、読み直しの範囲に入っても拾わない（既に実行済み）。
- **RESUME で Discord が送り直してくれた分**は、その時点で普通に実行されるので、読み直しでは拾わない。
- **読み直しで拾ったあとに、同じメッセージが遅れて Discord から届いても**、もう一度は実行しない
  （ログに `already picked up after a gateway outage — not running it twice` が出る）。
- **切断と復帰が何度続いても**、一度拾ったメッセージは拾い直さない。
- **このプロセスが起動する前のメッセージ**は読み直さない。前のプロセスが既に実行している
  かもしれないため。

### 境界

- **接続が戻ったあと、読み直しより先に新しい依頼を送っていたら、そちらが優先される。**
  古い依頼をいま実行すると新しい依頼を割り込みで止めてしまうので、古い方は実行せず、
  1 行で「そのあとに届いた依頼を先に処理しているので、こちらは実行していません。必要なら
  もう一度送ってください。」と出る。
- **手動で停止した（`/workspace-stop`）スレッド**への投稿は、その場で届いた場合と同じく
  実行されず、再開ボタン付きの案内が出る（[session-close.md](./session-close.md)）。1 行の案内は
  「受け取れていませんでした」までで、「いまから処理します」とは言わない。
- **読み直す開始点は「切断に気づいた時刻」ではなく「最後に何かが届いた時刻」の少し前**
  （2 分前）。ホストのスリープやプロセスの一時停止では、切断に気づくのは再開した後なので、
  気づいた時刻から読むとその間の投稿を取りこぼすため。範囲を広めにとっても、既に届いた
  ものは上のとおり拾わないので二重にはならない。
- **1 スレッドで読み直すのは最大 100 通。** 超えたらログに WARNING が出る。
- **スレッドを 1 本ずつ全部読むことはしない。** サーバーごとにアクティブなスレッドの一覧を
  1 回取り、最後の投稿が読み直し範囲に入っているスレッドだけを読む。短い再接続（Discord が
  日に何度か求めてくるもの）では、読むスレッドはほぼ 0 本になる。

### 拾わないもの（スコープ外）

- **c-lord のセッションが無いスレッド・チャンネル**（他の c-lord インスタンスのスレッドを含む）。
  その場で届いた場合も実行しないものは、読み直しても実行しない。30 日スイープで記録が消えた
  スレッド（[session-resume.md](./session-resume.md) の「記録が無い」）も対象外。
- **テキストコマンド（`!stop` など）。** 何時間も後に `!stop` が走るのは誰も頼んでいない動きなので、
  自動では実行しない。
- **切断中に自動アーカイブされたスレッド。** 投稿でアーカイブは解除されるが、切断が
  そのスレッドの自動アーカイブ期間（既定 3 日）より長いと、再びアーカイブされて一覧に出ない。
- **c-lord のプロセスが止まっていた間（再起動中）の投稿。** これは「接続が切れていた」のでは
  なく「c-lord がいなかった」ケースで、別 Issue で扱う。
- **切断中に c-lord が Discord へ書こうとして失敗した出力**（Claude の返事など）の再送。

### エラー時

- **読み直しに失敗しても、bot は止まらない。** サーバー単位・スレッド単位で失敗したものは
  WARNING でログに残し、残りは続ける。
- **1 行の案内の投稿に失敗しても、依頼の実行は止めない。**

## バグの例（こうなっていたらバグ）

- 切断中にスレッドへ送った依頼に、接続が戻っても**リアクションも返事も付かない**（#745 そのもの）。
- 接続が戻ったあと、**同じ依頼が 2 回実行される**（返事が 2 つ来る、⚡ Interrupted が出る）。
- 切断の直前に送って既に返事をもらった依頼が、復帰時に**もう一度実行される**。
- 取りこぼしが無かったスレッドに 🔌 の 1 行が出る。
- 切断中に 2 通送ったら、2 通目が 1 通目を ⚡ で止め、**1 通目の内容が Claude に届かない**。
- 切断があったのに、ログを `grep "Gateway outage"` しても**何も出ない**。
- 他の c-lord インスタンスのスレッドに、この c-lord が 🔌 の案内を出す。

## 根拠

- #745 — 2026-09-16、ホストの DNS 障害で本番 bot が 6時間35分 gateway から切れ、その間に
  c-lord スレッドへ送られた 2 通が無言で消えた。送り主は 4時間半後に同じ文面を再送した。
- #537 — 同じ消え方を「c-lord 自身がイベントループを止めて heartbeat を落とす」原因側で塞いだ。
  原因を 1 つずつ潰しても次の切断で同じことが起きるので、#745 は復帰時に取りに行く側で塞ぐ。
- #678 / #681 / #538 / #554 — 「失敗を無言にしない」。Discord との接続そのものにも適用する。
- #315 / USER_GUIDE「Interrupting」— 新しいメッセージは走っているターンに割り込む。まとめて
  1 ターンにする・新しい依頼を優先する、はこの割り込みで依頼が消えないようにするため。
- 実装: `c_lord/gateway_backfill.py`（開始点と既読の管理・文言）、
  `c_lord/cogs/claude_chat.py`（`on_disconnect` / `on_resumed` / `on_ready` からの読み直し）。
