# あるべき動き: スケジュール実行（定期タスク）

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

「毎週金曜 11:00 に、このプロンプトを Claude に実行させる」を登録しておく機能です。登録は Discord のセッション中に Claude が `POST /api/tasks` を叩くか、DB の `scheduled_tasks` に直接入れます。

時間が来ると、c-lord がチャンネルに `🔄 **[Scheduled]** <タスク名>` を投稿し、**そのメッセージにスレッドを付けて**、そのスレッドの中で Claude を走らせます。利用者から見ると「自分が打っていないのに、勝手にスレッドが立って作業が進み、結果が投稿される」のがこの機能です。

**依頼した人はその時間に画面を見ていません。**「動いた/動かなかった」がスレッドとログにはっきり残ることが、この機能では通常のチャットより重要です。

## あるべき動き（利用者から見て）

### 正常時

- **時間になったら 30 秒以内にスレッドが立つ**（master loop の刻みが 30 秒のため）。
- **スレッドの中で Claude が実際に起動する。** 使うディレクトリはタスクに登録した `working_dir`（未指定なら bot の既定ディレクトリ）で、**tmux ウィンドウもそのディレクトリに作られる**。`tmux attach` で人が覗ける状態になる（普通のチャットのスレッドと同じ扱い）。
- **プロンプトに対する Claude の応答がスレッドに投稿される。** ツールの実行 embed だけが並んで本文が来ない、という状態にはならない。
- **同じタスクの前回の実行スレッドは、もう更新されない。** 毎回のスレッドはその回の実行だけを映す。
  **bot を再起動しても同じ**（再起動で前回のスレッドが復活して二重投稿になったのが #719）。
- **終わったあと、そのスレッドは実行の記録として残る。** 閉じない — 報告を読んで返信できる場所として
  開いたまま置く(#687)。更新が止まるだけで、`/close-workspace` や通常のアイドル休眠
  ([workspace-sleep.md](./workspace-sleep.md)) は普通のスレッドと同じように効く。
- **そのスレッドに返信すると、その実行の続きとして Claude に届く。** スケジュール実行のスレッドは「読んで終わり」ではなく、報告を読んだ人がその場で追加指示を出す場所です。返信は**その回が使った `working_dir`（固定 checkout）のまま**続きます — 返信のたびに別のディレクトリが用意されたり、ワークスペースが引っ越したりはしません(#687)。

### 境界

- **同じタスクがまだ走っている間に次の実行時刻が来たら、二重には走らせない**（前回が終わるまでスキップする）。
- **前回の実行と今回の実行は同じ `working_dir` を共有する。** それでも、今回の出力が前回のスレッドに二重投稿されることはない。
  - **この形（固定 `working_dir` + 実行ごとに新しいスレッド）は変えない** — 決定 (#719 AC4)。
    各回の報告がその回のスレッドに独立して残り、そこに返信できる(#687)ことがこの機能の価値なので、
    「毎回別ディレクトリを切る」も「1 本のスレッドを使い回す」も採らない。
    代わりに、共有される transcript の側に「**映してよいのは、いま turn を始めたスレッド 1 本だけ**」
    という規則を置く（[transcript-mirror-replay-safety.md](./transcript-mirror-replay-safety.md)
    §「1 つの transcript を読むミラーは 1 本だけ」）。前回のスレッドは**閉じない**。
- **`working_dir` を登録していないタスク**は bot の既定ディレクトリで走る。ウィンドウと Claude が別々のディレクトリを向くことはない。
- **スケジュール実行のスレッドも、普通のスレッドと同じ「セッション」として記録される。** だから返信で再開できるし、bot を再起動しても回答の経路(jsonl ミラー)が戻ってくる。「c-lord が立てたスレッドなのに c-lord の記録に無い」という状態は作らない(#687)。
- **チャンネルが `/clord-init` で repo に紐づいていない**場合、スケジュール実行はできない。その事実がログに残る。

### エラー時

- **起動できなかったときは、その理由が本当のことでなければならない。** 特に「**ウィンドウが作られていない**」と「**ペインが落ちている / 入力を受け付けない**」は、原因も対処もまったく違うので、同じ文言にまとめない。
  - ウィンドウが無いとき: 「このスレッド用の tmux ウィンドウが作られていません」と言い、`/restart-claude` は案内しない（既存のペインを立て直すコマンドなので、無いウィンドウは作れない）。確認すべきは repo の紐付けと、ホストで tmux が使えるかどうか。
  - ペインが応答しないとき: 従来どおり `/restart-claude` を案内する。
- **失敗したら、スレッドが空のまま終わらない。** 何が起きたかを 1 通は投稿する。
- **失敗したら、bot ログに ERROR / WARNING が残る。** `_run_task: enter` → `_run_task: exit` だけが並んで、正常終了と見分けが付かない状態にはならない。
- **例外で落ちた場合もスタックトレース付きでログに残る**（従来どおり）。

## バグの例

- **時間になるとスレッドは立つが、中身が ❌ Error 1 件だけで終わる。** Claude が一度も起動していない（#621。`_run_task` が tmux ウィンドウを作らずに起動しようとしていた）。
- **そのエラーが「ペインが落ちているか応答しない状態です。`/restart-claude` でセッションを立て直してください」と案内する。** ウィンドウが一度も作られていないのだから、案内どおりにしても直らない（#621）。
- **ツール実行の embed だけが流れて、Claude の回答本文がスレッドに来ない。** 応答を運ぶ経路（jsonl ミラー）が張られていない（#621）。
- **入口と出口のログだけが 2 秒で並び、失敗したことがログから読み取れない**（#621）。
- **先週のスレッドに今週の実行のログが流れ込む。** 前回の実行のミラーが止まっていない（#621）。
- **いったん直ったはずのそれが、bot の再起動で戻ってくる。** 前回スレッドのミラーを止める記憶は
  `SchedulerCog` のメモリにしか無く、再起動でそれだけが消える一方、`on_ready` は
  「閉じていない行」として前回スレッドのミラーを張り直していた（#719。2026-09-04 に終わっていた
  スレッドへ、2026-09-11 の週次精査が完了報告まで丸ごと流れ込んだ）。週次タスクでは
  **実行のたびに二重投稿の相手が 1 本ずつ増える**のが特に重い。
- **報告を読んで返信すると「⚠️ このスレッドには復元できるワークスペースがありません」と拒否される。** tmux ウィンドウはその瞬間も生きているのに、`sessions` 行が書かれていないので c-lord から見えない（#687。2026-09-04 の週次精査スレッドで、620k コンテキストを積んだセッションに 2 通が届かなかった）。

## 根拠

- #90 — スケジューラの導入（SQLite backed、30 秒 master loop）。「Claude が『何を』、c-lord が『いつ』を持つ」（CLAUDE.md §Key Design Decisions 9）。
- #621 — スケジュール実行が tmux ウィンドウを作らずに必ず失敗していた件。この spec はそのとき「あるべき動き」を書き起こしたもの。
- #585 / #477 — 黙って失敗する・起動失敗がスレッドに分かりやすく出ない、の系列。エラー時の項はこの系列の延長。
- #687 — スケジュール実行のスレッドに返信できなかった件（`repo=None` で `sessions` 行が書かれず、#538 の UNTRACKED 判定に落ちていた）。「返信できる」を正常時の動きとして書き起こしたのはこのとき。固定 checkout を返信のたびに session dir で上書きしない規則は [`c_lord/workspace_dir.py`](../../c_lord/workspace_dir.py)。
- #719 — 同じ `working_dir` を持つ 2 スレッドに同じ transcript がミラーされていた件。
  「毎回新しいスレッドを立てる」形を残すと決め(AC4)、衝突は transcript の所有規則で解いた。
- 理念: [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md)。定期実行は「見ていない間に進む」ことが価値なので、**見ていない間に静かに壊れる**のがこの機能で一番重い失敗。
