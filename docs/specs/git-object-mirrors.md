# あるべき動き: 作業ディレクトリが git オブジェクトを共有する

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

決定の経緯は #577 → #643。用語は [`workspace-vocabulary.md`](workspace-vocabulary.md) に従う。

## なぜこの文書があるか

**同じリポジトリを何十回もクローンすると、同じ中身を何十個も持つことになる。**

本番実測 (tachikoma / 2026-08-31):

| | |
|---|---:|
| `c-lord-sessions` 合計 | 121 GB |
| うち1リポジトリ (`project_30_ehon-ya`) の240クローン | **117 GB** |
| その `.git` だけの合計 | **39.2 GB** |
| 同じリポジトリの**全履歴 bare ミラー1個** | **256 MB** |

240個の `.git` は**中身が同じ**。それでも合計が 39 GB に膨らむのは、`--depth=1` の
クローンがそれぞれ独立した pack を持ち、共通部分の圧縮が効かないため。GitHub 側が
まとめて repack したものを1個もらえば 256 MB で足りる。**まとめると 256 MB、
バラすと 39 GB** — これが節約の正体で、この文書が存在する理由。

なお **240件中229件は `sessions` の行が生きている**。#613 の孤児掃除も #575 の
行スイープも、これらには（正しく）触れない。生きている作業ディレクトリが、
必要のない同じデータを229回持っている状態だった。

## あるべき動き

### 置き場所

```
c-lord-sessions/                      ← セッション root
├── .mirrors/                         ← 共有オブジェクトの置き場
│   ├── README.md                     ← 何か・消したらどう直すか
│   └── github-com-kater-iam-project-30-ehon-ya-<12桁>.git
├── 1440498354797674496/              ← チャンネル
│   └── 1540583883047698493/          ← 作業ディレクトリ (.git は 1.2 MB)
```

- **セッション root の中に置く。** そうすると**節約する対象と必ず同じディスクに乗る** —
  セッションを大きいディスクに移した利用者がいても、ミラーが自動的についてくる。
  `~/.cache` を使わないのは、XDG が「いつ消してもよい」と規定していて意味が真逆になるため
- **名前は数字でない。** ワークスペースは `<root>/<channel>/<thread>` という全部数字の形なので、
  数字でない名前は #613 の掃除の候補に**構造的に**上がらない（`orphan_dirs._workspace_dirs`
  が入口で `isdigit()` を見る）。テストで固定してある
- **ドット始まり。** `rm -rf <root>/*` が当たらない
- **リポジトリ1種につき1個。** `git@github.com:a/b.git` / `https://github.com/a/b.git` /
  `https://github.com/a/b` / `ssh://git@github.com/a/b.git` は**同じ**ミラーに解決される。
  ここが分かれると節約が丸ごと消える（実測で `yousan/c-lord` は3表記に分かれていた）

### クローンのとき

```diff
- git clone --depth=1 --single-branch -- <url> <target>
+ git clone --depth=1 --single-branch --reference-if-able <mirror> -- <url> <target>
```

1. ミラーが無ければ `git clone --mirror` で作る
2. ミラーがあれば `git fetch` で更新する（`--prune` は**しない** — upstream で消えた
   ブランチのオブジェクトを参照しているクローンが在りうる）
3. どちらも**失敗してよい**。失敗したらミラー無しでクローンする

**ローカルリポジトリ (`git clone --local`) はミラーを使わない。** 既に hardlink で
共有しており、意味が無い（実測: `/home/yousan/c-lord` の300クローンで合計 0.5 GB）。

### 利用者から見た変化

**無い。** 変わるのは `.git` のサイズだけ。

| 操作 | 共有後 |
|---|---|
| ブランチを切る / 行き来する / コミット | 変わらない |
| push / pull / fetch | 変わらない |
| diff / blame / stash | 変わらない |
| `git fsck` | クリーン |
| `--depth=1` の浅さ | 変わらない (`shallow` は有効なまま) |
| クローン所要時間 | **速くなる**（ネットワーク転送がほぼ消える。実測 3.8 秒） |

## 守らなければならない不変条件

### 1. ミラーが無くても・作れなくても、クローンは成功する

**ミラーは高速化と節約のためのものであって、動作の前提ではない。** `git_mirrors` の
あらゆる失敗は `None` を返して終わり、呼び出し側はそれを「`--reference-if-able` を
付けない」にしか使わない。`session_dir._mirror_for_clone()` に広い `except` が
置いてあるのも同じ理由で、**この最適化のためにスレッドが立たなくなるのは割に合わない**。

`--reference-if-able` の `-if-able` も同じ保険で、ミラーのパスが消えていても
git は info を1行出して通常のクローンに落ちる（実測確認済み）。

### 2. ミラーのパスが置き場の外に出ない

origin URL は `/clord repo:` で**利用者入力**から届く (#514)。ミラー名は
正規化後の URL のダイジェスト＋`[A-Za-z0-9_-]` だけの slug で作る。slug から `.` を
落としてあるので `..` は構造的に作れない。加えて、解決後のパスが置き場の直下に
あることを実行時にも確認する。

### 3. ミラーは足すだけ。自分のオブジェクトを刈らない

ミラーは**参照されている側**なので、オブジェクトが消えると参照しているクローンが壊れる。
作成時に `gc.auto=0` を設定する。`fetch --prune` もしない。

### 4. 半端なミラーを絶対に残さない

オブジェクトが欠けたミラーを参照したクローンは壊れる。一時ディレクトリに
`clone --mirror` してから `rename` するので、置き場のパスは
**「存在しない」か「完全」のどちらか**しか取りえない。

## ミラーが消えたらどうなるか

**ミラーは derived data。** 中身は origin にあるものの写しでしかなく、失われる情報が無い。
`sessions.db` のような「消えたら戻らないもの」ではない。

| | 消した直後 | 作り直したあと |
|---|---|---|
| **作業ファイル** | **無傷** | 無傷 |
| **未コミットの変更** | **無傷** | 無傷 |
| `git status` | エラー行を出すが動く | 正常 |
| 履歴を読む | `fatal: Failed to traverse parents of commit ...` | 正常 |
| `git fsck` | — | クリーン |

**c-lord が次にクローンするとき自動で作り直す**（実測 28 秒で完全復旧）。
だから `rm -rf c-lord-sessions` の被害は「次のクローンが数十秒余計にかかる」で終わる。

失いたくないもの（未コミットの作業）は git の管理外なので、**そもそも危険にさらされない**。

## 切り戻し

**新規クローンの挙動を戻す**: `CLORD_GIT_MIRRORS=0` を設定する（既定は有効）。
次のスレッドから `--reference-if-able` が付かなくなる。

**既存のクローンをミラーから独立させる**: そのクローンで

```bash
git repack -a -d && rm -f .git/objects/info/alternates
```

実測で 3.7 MB → 257 MB になり、ミラーを消しても動作した（log / status / fsck すべて green）。
**片道の変更ではない。**
