# あるべき動き: 役目を終えた作業ウィンドウの後片付け

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

C-lord は、スレッドごとに tmux のウィンドウを作って作業します（→ [tmux-layout.md](./tmux-layout.md)）。
このファイルは「**そのウィンドウが、役目を終えたあとどうなるか**」を決めるものです。

`tmux ls` / `tmux attach` は、いま何が動いているかを人が見に行く唯一の窓口です。
**そこに何ヶ月も前の空っぽの窓が並んでいると、現役の窓が埋もれて見つけられなくなります。**
2026-08-31 に yousan が attach 先を見失った件（#616 / #618）はこれが直接の原因でした。

## あるべき動き（利用者から見て）

### 正常時

- **C-lord が作った窓は、役目を終えたら放っておいても消えます。** 手で消して回る必要はありません。
- 掃除は **bot の起動時に1回**走ります。定期的に見回るループはありません。
- **`tmux ls` に残るのは、現役の窓と、人が自分で作った窓だけ**になります。

### 絶対に消えないもの

ここが本体です。**消し過ぎは取り返しがつかない**ので、下のどれか1つでも当てはまる窓は消しません。

| 窓 | なぜ残すか |
|---|---|
| **何かが動いている窓** | 中の作業が失われます。Claude はもちろん、開発サーバでもビルドでも同じです。「空のシェルが出ているだけ」の窓だけが対象です |
| **人が手で作った窓** | C-lord の管轄外です。人は窓に**中身の名前**を付けます（`factorio3`, `minecraft`, `rig`）。C-lord が付ける `w5` / `work12` という形とは重なりません |
| **いま使われているスレッドの窓** | 現役です |
| **別の C-lord が作った窓** | 1つの tmux サーバを複数の C-lord（本番と staging、別々の bot など）が共有していることがあります。掃除する側は**自分の**スレッドの状況しか知らないので、別の C-lord が窓を作って Claude を起動するまでの数秒間の窓は「空」に見えます。それを消すと相手のスレッドの1通目が消えます（#790）。別の C-lord の窓は、その C-lord 自身が起動時に片付けます |

**作業ディレクトリの場所は判定に使いません。** 人が手で作った窓が、たまたま C-lord の作業ディレクトリに
`cd` していることがあるからです（`tachikoma1` の Factorio 運用窓がまさにこれ）。
逆に、C-lord の残骸のほうは作業ディレクトリを失っていることが多く、場所で見ると**逆の結果になります**。

### 境界

- **どの C-lord の窓かは、作ったときに窓に付ける `@clord_owner` という目印で見分けます**（#790）。
  値は既定で「その C-lord を起動したディレクトリ」です。C-lord はそれぞれ別のチェックアウト／インスタンス用リポジトリから
  起動されるので、設定なしで区別できます。同じディレクトリから2つ起動する特殊な構成では `CLORD_INSTANCE_ID` で名前を付けます。
  目印は `@thread_id` と**同じ1回の tmux 呼び出しで**付けるので、「スレッドの目印はあるが持ち主の目印が無い」瞬間はありません。
- **`@clord_owner` の無い窓は、これまでどおり下のルールで判断します。** #790 より前に作られた窓と、
  ホスト再起動で目印を失った窓がこれに当たります（どちらも「持ち主が分からない」だけで、持ち主が別だという証拠はありません）。

- **`@thread_id` という目印を失った窓も、ちゃんと消えます。** これは tmux の内部的な目印で、
  **ホストを再起動すると必ず失われます**（tmux-resurrect が窓の名前は復元するが、この種の設定は保存しないため）。
  目印がある窓しか消さない作りだと、**再起動をまたいだ窓は永久に消えなくなります**。
- 目印を失った窓は、**窓の名前**（`w5` / `work12`）で C-lord のものだと判断します。
  名前は再起動をまたいで残る唯一の目印で、かつ **C-lord が機械的に付けた形**だと見て分かるからです。
- **人が窓を `work3` と名付けていた場合でも、中で何か動いていれば残ります。** 空のシェルが出ているだけの
  `work3` は消えます。名前だけで消すことはしません。
- **セッション（`games`, `pt-jp` など）の最初の窓（`zsh` など）は消しません。** C-lord の作業窓ではないからです。

### エラー時

- **tmux が答えないときは、消さずに残します。** 「中で何が動いているか分からない」は「空だ」ではありません。
- **1つのセッションの掃除に失敗しても、他のセッションの掃除は続けます。**
- **消したものは1件ずつログに残ります。** セッション名・窓の名前・窓の ID・作業ディレクトリ・消した理由が1行に出ます。
  件数だけだと、あとから「何が消えたのか」を追えません（`grep "tmux reaper"` で全件たどれます）。

## バグの例

- 空の作業窓が何ヶ月も `tmux ls` に残り続ける。2026-09-02 に手で15本消したが、**2026-09-04 には18本に戻っていた**（#677）
- 人が手で作った窓（`tachikoma1:factorio3`）が、作業ディレクトリが C-lord のものだからという理由で消される
- 中で開発サーバが動いている窓が、名前が `work3` だからという理由で消される
- staging を再起動した瞬間に、**別の C-lord が作ったばかりの窓**が消され、そのスレッドの1通目が失われる（#790）
- 掃除のログが `killed 1 orphaned window(s)` だけで、**何が消えたのか分からない**（#677 以前の挙動）

## 根拠

- #570 — 掃除の仕組みそのもの。定義だけあって呼ばれておらず、空の窓が175本溜まっていた
- #677 — 本ドキュメントの発端。`@thread_id` を失った窓が掃除の対象外になり、**永久に**溜まり続けていた。
  調査の結果、目印が失われるのは tmux-resurrect が窓のオプションを一切保存しないためで、
  **ホスト再起動のたびに C-lord の全窓で起きる**ことが分かった
- #790 — 1つの tmux サーバを共有する別の C-lord の、起動直後の窓を消していた（2026-09-23、staging-4 の再起動が
  staging-2 の新しいスレッドの窓を1秒後に消した）。掃除する側は自分のスレッドの状況しか知らないため
- #69 / #113 — 目印を失った窓を、生きているスレッドのために復旧する仕組み。
  「現役を救う」ためのもので、「役目を終えた窓を掃除可能に戻す」ためのものではない
- #616 / #618 — 溜まった窓で attach 先を見失った実例
- [tmux-window-identity.md](./tmux-window-identity.md) — 窓をどう同定するか（`@thread_id` と名前の役割分担）
- 理念: 「複数を並行して進める」が核である以上、**いま何が動いているかを人が見て分かること**はその前提
