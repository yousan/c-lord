# あるべき動き: セッションの終了と再開（/close-workspace）

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

**終了**（`/close-workspace`）は、そのスレッドの作業をいったん**畳む**操作です。tmux ウィンドウを閉じてスレッドをアーカイブしますが、**会話の履歴・作業ディレクトリ・セッションのレコードは残します**。あとでいつでも続きから再開できます。

似て非なる 2 つと区別してください:

| | 何が起きるか | 次にメッセージを送ると |
|---|---|---|
| **終了** `/close-workspace` | ウィンドウを閉じる。履歴・作業ディレクトリは残る | **実行されない**。終了案内＋再開ボタンが出る |
| **落ちた（dead）** bot 再起動 / tmux サーバ死 / `kill -9` | 意図せずウィンドウが消えた。履歴は残る | **黙って復元されて実行される**（`--continue`, #270） |
| **削除** `/workspace-delete` | ウィンドウも作業ディレクトリも消す | 再開できない（新規セッション扱い） |
| **記録が無い** DB を作り直した / 別ホストのスレッド | c-lord から見て初めて見るスレッド | **実行されない**。復元できない旨と次の一手が出る（#538) |

3 つの状態それぞれで「メッセージを送ったら何が起きるか」と「止まっているときの案内文」は[session-resume.md](./session-resume.md) が正本です。

なぜ「終了」と「落ちた」を分けるか: **利用者が自分で終わらせたのか、事故で消えたのかは、次に何をすべきかがまったく違うから**です。事故なら黙って直してほしい（#464 の tmux サーバ死のとき、黙って直らないことが問題だった）。自分で終わらせたなら、勝手に動き出さないでほしい。両方を「ウィンドウが無い」という同じ観測だけで扱うと、必ずどちらかの体験が壊れます。だから終了は**観測ではなく事実として記録**します（`sessions.closed_at`）。

## あるべき動き（利用者から見て）

### 終了するとき

- **スレッド名の先頭が `[終了]` になる。** `W3 │ #404 認証リファクタ` → `[終了] #404 認証リファクタ`。一覧・アーカイブ一覧で「これは終わった作業」と一目で分かる。詳しい形は [thread-name.md](./thread-name.md)。
- **スレッドはアーカイブされる**（サイドバーから畳まれる, #271）。
- **完了メッセージに、終了後の名前と再開方法が出る。**
- **履歴と作業ディレクトリは消えない。** ディスクを空けたいときは `/workspace-delete`（こちらは再開できない）。

### 終了済みスレッドに投稿したとき

- **そのメッセージは Claude に渡らない。** 実行されない。
- **代わりに案内が出る**: 「⏹️ このスレッドは終了しています」＋「送信されたメッセージは実行していません」＋再開方法。
- **案内に「▶️ 再開する」ボタンが付く。** 押すと再開し、**いま送ったメッセージがそのまま実行される**（打ち直し不要）。
- **`/reopen-workspace`（`!reopen-workspace`）でも再開できる。** こちらはメッセージの再送はしない（再開するだけ）。

### 再開したとき

- **名前から `[終了]` が消える。** `W<番号> │` は、次のメッセージで実際に tmux ウィンドウが立ってから戻る（存在しない番号を先に書かない）。
- **会話は続きから再開する**（`--continue`）。案内は「🔄 終了していたセッションを復元して、続きから再開します。」
  - 落ちていたセッションの自動復元（#464）とは**文言が違う**。あちらは「前回のセッションが落ちていたので…」。自分で終了させた人に「落ちていた」と言うのは事実に反するし、新しい障害が起きたように読める。

### 境界

- **終了していないスレッド**は一切影響を受けない。落ちたペインの自動復元（#270 / #464）は従来どおり黙って動く。
- **二重クリック**しても、握られていたメッセージが 2 回実行されることはない（再開済みのボタンは無効化され「再開済みです」と返す）。
- **リネームできないとき**（bot に「スレッドの管理 / Manage Threads」権限が無い等）でも、終了そのもの・アーカイブ・再開導線は成立する。名前は飾りであって、状態の正本は DB 側。
- **60 秒ごとのサイドバー同期**は終了状態を尊重し、`[終了]` を剥がさない。
- **終了中に手でスレッド名を変えても**、`[終了]` がトピック本体に取り込まれて二重化（`[終了] [終了] …`）することはない。

### エラー時

- **リネーム失敗はアーカイブを巻き添えにしない。** 名前を変えられなくても、終了は完了する。
- **改名とアーカイブは 1 回の操作でまとめて行う。** Discord はスレッド名の変更を **10 分におよそ 2 回**しか許さず、しかも**アーカイブ済みスレッドの編集は拒否する**。別々に 2 回投げると、この枠を 2 つ使ううえ、アーカイブが先に効いた瞬間に改名が弾かれる。まとめて 1 回にすることで、枠の消費を半分にし順序の事故も無くす。
  - それでも枠を使い切っていた場合は待って再試行する（この待ちの間、終了コマンドの返信は少し遅れる）。待ちきれなかったときは `[終了]` が付かないまま終わることがあるが、**終了そのもの（投稿のブロックと再開導線）は DB 側の記録で成立している**ので機能は失われない。ログに警告が残る。
- **案内の投稿に失敗しても、メッセージが黙って実行されることはない。** 終了しているスレッドは、案内の成否にかかわらず実行しない。

## バグの例（こうなっていたらバグ）

- `/close-workspace` したのにスレッド名が `W3 │ …` のまま（終了と見分けられない）。
- 終了済みスレッドに投稿したら Claude が動き出した。
- 終了済みスレッドに投稿したのに、何の反応も無い（案内が出ない）＝黙って握り潰されている。
- 再開したのにスレッドがアーカイブされたまま（サイドバーに戻らない）。
- 再開ボタンを押したのに、送ったメッセージが実行されず打ち直しになる。
- 自分で終了させて再開したのに「前回のセッションが落ちていたので」と言われる。
- **落ちただけ**のスレッド（bot 再起動後など）に投稿したら、終了案内が出て自動復元されなくなった（#270 / #464 の退行）。

## 関連コマンド

| コマンド | 何をするか |
|---|---|
| `/close-workspace` / `!close-workspace` | 終了する（ウィンドウを閉じる・履歴は残す） |
| `/reopen-workspace` / `!reopen-workspace` | 終了を解除する |
| `/workspace-delete` / `!workspace-delete` | 作業ディレクトリごと削除（再開できない） |
| `/clord-status show_all:true` | 終了済みを含めて一覧する |

## 根拠

- #271 — `/close-workspace` の導入（削除ではない「畳む」操作）。
- #379 — 終了時に TranscriptMirror を先に止める（アーカイブ直後の 👤 echo でスレッドが開き直る問題）。
- #270 / #464 — 落ちたペインの `--continue` 自動復元と、その告知。本 spec の「終了」とは別経路。
- #512 — 終了を `closed_at` として記録し、`[終了]` 表示・投稿ブロック・再開導線を追加。
