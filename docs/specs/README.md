# あるべき動き（spec）の一覧

> **#574 で改名**: 操作名は「終了」→「**停止**」、コマンドは `/close-workspace` → `/workspace-stop`、`/reopen-workspace` → `/workspace-start`、スレッド名のマーカーは `[終了]` → `[停止]` になりました。**旧コマンド名はエイリアスとして動き続けます**（利用者側の変更は不要）。既存スレッドに残る `[終了]` も引き続き正しく解釈されます。理由: 7日で自動発火するようになるため、何も失っていないのに「終了」と言われると誤解を招くから。詳細は [workspace-vocabulary.md](workspace-vocabulary.md)。

各機能が「**本来どう動くべきか**（利用者から見て）」を1機能1枚で書いたものの索引です。

> このフォルダは、理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下にぶら下がります。
> 理念は「なぜ C-lord が在るか」を決め、各 spec は「その下で、各機能がどう動くべきか」を決めます。
> 理念だけからは各機能のあるべき動きは出てこない、と理念自身が言っています（[理念の限界](../PHILOSOPHY.md#理念の限界)）。その穴を、ここの spec が埋めます。

## なぜこれが要るか

「これは仕様? バグ?」を判断するには、見比べる相手＝「本来どう動くべきか」を書いたものが要ります。
それが無いと、コードを読んで「コードがこうなっているから仕様」と言うしかなくなりますが、コードは意図を語れません。
そこで、機能ごとに「あるべき動き」を文章で先に固定しておき、実際の動きと突き合わせて仕様かバグかを見分けられるようにします。

## 書き方（型）

新しい spec を足すときは、下の並びで1ファイル1機能で書きます。難しい言葉は避け、利用者から見た言葉で書いてください。

1. **冒頭の位置づけ** — 各ファイルの先頭に、次の一文をそのまま置く:

   > これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

2. **これは何か** — その機能を1〜2文で。利用者が何を見る/何が起きるか。

3. **あるべき動き** — 次の3つに分けて、利用者から見た言葉で書く（ここが本体）:
   - **正常時** — ふつうに使ったとき、こう動くべき。
   - **境界** — ぎりぎりの場合（ちょうど上限ちょうど、空、とても長い、など）にどうなるべき。
   - **エラー時** — 失敗したとき・途中で止まったときにどうなるべき。

4. **バグの例** — 「こうなっていたらバグ」を具体的に1〜数個。仕様と取り違えやすいものほど価値が高い。

5. **根拠** — このあるべき動きを決めた経緯（Issue / PR 番号、理念のどの部分か）。

### ルール

- **1ファイル＝1機能。** タイトルに「と」が要るなら、たぶん2機能なので分ける。
- **利用者の言葉で書く。** 関数名・行番号・内部の仕組みは原則書かない（そこは spec の役目ではない）。
- **判断できる形で書く。** 「だいたい」「たぶん」ではなく、見れば白黒がつくように書く。
- **動きを変えたら spec も直す。** 機能の動きを変える変更をしたら、対応する spec を同じ PR で更新する（このルールの徹底と既存のズレ直しは別 Issue）。
