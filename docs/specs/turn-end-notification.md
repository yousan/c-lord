# あるべき動き: ターン終了の呼び出し（🟡 / ⚠️）

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

ターンが終わると、そのターンを頼んだ人にメンション付きのメッセージが 1 通届きます。これは**呼び出し**です — 利用者はやっていたことを中断して見に来ます。

だから**内容が事実と食い違ってはいけません**。「終わりました」と言われて見に行ったのに何も返っていなければ、その通知は次から読まれなくなります。

## あるべき動き

### 正常時 — 応答があったターン

```
🟡 Claude has finished — your reply is needed here. @依頼者
```

- 出るのは **PROCESSING → WAITING_INPUT の遷移時に 1 回だけ**
- メンションは**そのターンを頼んだ人**（スレッド作成者ではなく、そのターンの発言者）
- 人が頼んでいないターン（webhook / スケジュール実行）は `DISCORD_OWNER_ID` にフォールバック。設定が無ければメンション無しで投稿
- メンションは**文末**に置く。Discord のプッシュ通知のプレビューが「@you」ではなく本文で始まるようにするため
- **回答が届いた直後に出る**（数十秒以内）。呼び出しは「もう見に行っていい」の合図なので、遅れると意味を失う

### いつ「終わった」と判定するか（#583）

**Claude 自身の transcript が書く turn 終了マーカー**（`system/turn_duration`）で判定します。
既定の jsonl ブリッジでは回答はペインを通らないので、**ペインの静止を終了の根拠にしてはいけません**:

- 回答が届くとペインは完全に静止し、そこから取れる応答テキストは空になる →
  「非空の応答が安定」も「応答が空」も成立せず、ポーリングの完了判定はどちらも踏めない
- 逆にバックグラウンドタスクを抱えているとペインは**静止しない** → 無活動 backstop すら発火しない

マーカーは TranscriptMirror が読み、`c_lord.turn_end_bus` 経由でポーリングループに渡ります。

**transcript が「このターンはまだ続いている」と言っている間は、ペインの見た目だけでターンを閉じません**（#1132）。
具体的には、この run の開始後に Claude が読んだ指示が transcript にあり、そのあとにターンの終わりが無い間は、
ペインの判定（「応答が 3 秒変わらず入力欄が見える」・60 秒の無応答）が成立しても待ちます。
また、ミラーが transcript を読んでいるのに指示がまだ transcript に届いていない間（貼り付けとして送った長い依頼は、
Claude Code が API に送るときに初めて書かれる）も、ターン開始の猶予（120 秒）まで待ちます。

- 理由: 長い依頼（貼り付け扱い）では、Claude の最初の出力までの 15〜40 秒、ペインには生成中の表示が出ず、
  応答欄だけが前のターンと変わる。以前はここでペインの判定が成立し、送って 14〜19 秒で 📊・🟡・`completion` が出ていた
  （2026-10-29 の本番で 4 回。作業はそのあと最大 50 分続いた）
- transcript を読めないスレッド（ミラーがいない・記録が無い）では、従来どおりペインの判定で閉じる。ミラーが動いていても
  読む transcript が見つからず、c-lord が名付けた transcript（`.clord-session`）も無いか、名付けてから 120 秒たっても
  その transcript が現れないあいだは「読めない」側に数える
  （#1190 — 以前はミラーが起動しただけで「読んでいる」扱いになり、返事の届かないスレッドで 🟡 が送信の 120 秒後まで遅れた）
  - ただし名付けた transcript がまだ現れていないとき、その名前で**最初の依頼を送ってから** 120 秒は「読んでいる」側に数える
    （#1223 — 続ける会話の無いワークスペースを起こす（`/tmux-screenshot` など）と、その時点で名付けるが、transcript は最初の依頼で
    初めて書かれる。名付けた時刻から数えていたため、起こして 120 秒より後の最初の依頼でペインが早く閉じていた）。
    1 つの名前につき、その名前のもとで走った最初の 1 ターンだけ（新しく起動するときは、ターンの途中で名付けられるので、そのターンが最初の
    1 ターンになる。ミラーがターンと同時に起動して名前を見つけるのがターン開始より遅れても同じ）。その後も transcript が現れない名前は
    以後のターンを待たせない
  - どの名前の「最初の 1 ターン」を使い終えたかは bot のメモリにしか無い。bot を再起動すると、transcript が現れないままの名前でも
    再起動後の 1 ターンだけは最大 120 秒待つことがある（既知の制限 — #1223 のレビューで受け入れた）
  - 最初の 1 ターンが依頼を届ける前に止まった（⏹ Stop・割り込み）か、送信に失敗しても、そのターンが名前の 1 回分を使い切る。
    そのため 120 秒より後にやり直した依頼は、貼り付け扱いならペインの判定で早く閉じることがある（既知の制限 — #1223 のレビューで受け入れた）
- ターンの終わりを書かない古い CLI で永久に待たないよう、ペインが「終わった」見た目のまま 120 秒続いたら、
  WARNING を残してペインの判定で閉じる

**「そのターンの終わりか」は transcript の並び順で判定**します。transcript は 1 ターンを

```
user（Claude が読んだ指示）→ assistant … → system/turn_duration
```

の順で書くので、**このターンの開始より後に記録された指示があり、その後に終了マーカーが来た**
ときだけ、そのターンの終わりと見なします。割り込まれた前のターンのマーカーは「こちらの指示より前」
なので、新しいターンを終わらせません。

**「このターンの開始」は、c-lord がこのターンの依頼をペインに打ち込む直前の時刻**です（#916）。
Claude Code は指示に **Enter の瞬間の時刻**を付けるので、基準は打ち込む**前**に取ります。以前は
打ち込んで 1 秒待ってから基準を取っていたため、すぐ読まれた指示ほど基準より前になり、終了マーカーが
来てもターンが閉じませんでした（2026-10-09〜16 で 418 run 中 33 run しか効いていなかった）。
割り込まれた前のターンの指示はこの基準より前にあるので、その終了マーカーを取り違えることはありません（#365）。

**ペインの状態は一切見ません。** 長い回答は `●` マーカーが表示領域から流れ出て
「ターンが始まったか」すらペインからは判定できず（2026-09-08 の staging 実測）、
その状態で 300 秒 backstop まで待たされていたのが元の症状だからです。
マーカーが無い環境（古い CLI）では従来どおりペイン判定にフォールバックします。

### 割り込みで終わったターン（#583）

利用者の次の発言がターンを置き換えた（`⚡ Interrupted. Starting with new instruction...`）場合、
そのターンには**終了の儀式を一切出しません**:

- `🟡 Claude has finished` を**出さない**（📊 コンテキストフッタも出さない）
- 理由: 呼び出しは「見に来てください」の合図。**利用者はもう来ている**（いま話しかけた本人）。
  そこに「返信が必要です」と @ で呼ぶのは嘘であり、しかも新しいターンが1秒後に始まる
- ⏹ Stop ボタンで止めたターンは**これに含めない**。置き換えではなく利用者が終わらせた
  ターンなので、通常どおりの終わり方をする

### c-lord の再起動をまたいだターン（#907）

ターンの途中で c-lord が再起動しても（デプロイなど）、Claude はペインの中で作業を続け、回答は
transcript ミラーが届けます（#406）。このターンも**ふつうのターンと同じ終わり方**をします:

- 回答のあと、**📊 フッタ → `🟡 Claude has finished … @依頼者` の順に 1 回ずつ**出る
- 終わりの判定は、新しいプロセスがランプを引き取ったときの見張り（#718）が行う
  （transcript の終了マーカー、または transcript の読み直し）
- **再起動の間に既に終わっていたターン**も同じ。ミラーが取りこぼした回答を出し直す（#215）のを
  待つため、約 10 秒おいてから出す
- 呼び出す相手の決め方は通常と同じ（依頼者。webhook / bot のターンは `CLORD_OWNER_FALLBACK` に従う）
- **出さない場合**: 再起動後に同じスレッドで新しいターンが始まっていたとき（新しいターンが
  自分の終わりに出す — 割り込みで終わったターンと同じ理由）
- 📊 フッタの effort は出さない（前のプロセスが持っていた値で、もう分からないため）
- **終わり方は transcript から読む**（#978）。最後の返事が Claude Code の API エラーなら
  `❌ Claude Code が API エラーで止まりました。…`、プラン上限なら上限の文言で呼ぶ（このプロセスで終わった
  ターンと同じ文言 — #908 / #631）。「終わりました」と言うのは、ふつうに終わったターンだけ。
  外部向けのターン終了イベント（[turn-end-events.md](./turn-end-events.md)）も、この時点で 1 件出す

### 応答が 1 文字も無かったターン

```
⚠️ 応答がありませんでした — Claude がこのターンを開始しませんでした。もう一度送るか、tmux ペインを確認してください。 @依頼者
```

- **「終わりました」とは言わない。** 終わっていないため
- **呼び出しは行う。** 利用者は待っているので、黙って放置するほうが悪い
- あわせて `⚠️ 応答がありませんでした` の embed（次の一手つき）が出る

### 上限（クォータ）に当たったターン

```
⏳ Claude の weekly limit（上限）に達したため、このターンは実行されていません。Aug 29, 4pm (Asia/Tokyo) に回復します。それまでは送り直しても同じ結果になります。 @依頼者
```

応答が 1 文字も無い点は上と同じですが、**原因が分かっている**ので言うことが変わります。「もう一度送る」は上限が回復するまで通らないため、**言ってはいけません**。詳細は [usage-limit.md](./usage-limit.md)。

### 原因が分かっているターンの呼び出しは 1 回 (#915)

上限（上の節）・ログイン切れ・モデル使用不可・API エラー（下の 3 節）の 4 つは、どれも ❌ の embed がメンション付きで先に出ます（#681 — embed だけではプッシュ通知が飛ばないため）。embed には各節に書いた 1 行の内容がすべて（それ以上に）入っているので、**embed がすでに依頼者を呼んでいるときは、その 1 行は出しません**。依頼者へのメンションは**ちょうど 1 回**、案内の本文も 1 回（embed）です。

- 以前は embed のメンションと、この 1 行のメンションで**同じ人が 2 回呼ばれていました**（2026-10-15 実測）。同じ内容の呼び出しが 2 回来ると、次から読まれなくなります
- API エラー（#908）は #915 のあとに加わった原因で、当初この判定から漏れていました（#967）
- embed がメンションしなかった場合（呼ぶ相手が決まらなかったとき）や、呼んだ相手が違う場合は、従来どおりその 1 行がメンション付きで出ます
- 原因の分からない「応答がありませんでした」は対象外（embed と 1 行の両方が出ます）

### Claude Code のログインが切れていたターン (#812)

```
🔑 Claude Code のログインが切れているため、このターンは実行されていません。ホストで `claude` を開いて `/login` してください。ログインするまでは送り直しても同じ結果になります。 @依頼者
```

Claude Code はログインが切れていると、どの依頼にも `Login expired · Please run /login`（など `… · Please run /login` で終わる1行）だけを返して止まります。上限と同じく**原因が画面に出ている**ので、それを伝えます。

- **「開始しませんでした」「もう一度送る」とは言わない。** 直すにはホストで `/login` するしかなく、送り直しても同じ結果になるため
- **「終わりました」とも言わない。** 1行の拒否を「回答」とみなしてはいけない
- あわせて `🔑 Claude Code のログインが切れています` の embed が出る。ログインはホスト全体で共通なので、他のスレッドも止まっている可能性があることを添える
- 判定はペインの「`… · Please run /login` だけの行」がこのターンで**増えた**ときだけ。ステータス行の `Not logged in · Run /login` や、前のターンの行の再描画、文中で引用された文言では判定しない
- Claude が返した英語の1行（`Login expired · Please run /login`）は transcript ミラーがそのまま転送する（こちらは変えていない）

### 設定されたモデルを Claude Code が使えなかったターン (#484)

```
🧩 Claude Code がモデル `claude-nonexistent-zzz` を使えないため、このターンは実行されていません。`/model` で使えるモデルに戻してください。戻すまでは送り直しても同じ結果になります。 @依頼者
```

`/model` は形の正しいモデル ID なら何でも受け付け、使えるかどうかは Claude Code に任せています (#478)。Claude Code（2.1.283 で実測）は知らない／使えないモデルを渡されても**起動には失敗しません**。起動したうえで、どの依頼にも `There's an issue with the selected model (<モデル>). It may not exist or you may not have access to it. Run /model to pick a different model.` の1行だけを返して止まります。以前の c-lord はこれを普通の回答として扱い、🟡「終わりました」で閉じていました。

- **「終わりました」「もう一度送る」とは言わない。** 直すには c-lord の `/model` を変えるしかない
- あわせて `🧩 設定されたモデルを Claude Code が使えません` の embed が出る（❌）。`/model`（引数なし）で現在の設定を確認し、`/model` で戻すよう案内する。Claude Code の文言にある `/model` はペインの中のその1セッションしか変えないので、c-lord の設定である `/model` を名指しする
- 判定はログインのときと同じ: ペインの「`There's an issue with the selected model (…)` で始まる行」が**このターンのプロンプトの下に**出たとき（または、このターンで行数が増えたとき）。起動バナーに出るモデル名、前のターンの行の再描画、文中で引用された文言では判定しない
- Claude が返した英語の1行は transcript ミラーがそのまま転送する（こちらは変えていない）

### Claude Code が API エラーで止まったターン (#908)

```
❌ Claude Code が API エラーで止まりました。通信が途中で切れて、返事が途中で止まりました。『続けて』と送ると再開します。 @依頼者
```

API への接続が途中で切れた・サーバがエラーを返した・安全機能がセッションを止めた、などのとき、Claude Code は自分で英語のエラーを1件書いて（transcript では model `<synthetic>`・`isApiErrorMessage: true`）ターンを終えます。以前の c-lord はこれを普通の回答として流し、🟡「終わりました」で閉じていました。

- **ターンの最後のエントリ**がこのエラーなら、そのターンは **❌** で終わる。途中で出て CLI が自動で再試行し、Claude がそのあと普通に答えたターンは対象外（最後が普通の返事なので）
- 言うことは原因で変わる:
  - `… mid-response`（通信切れ・サーバエラーで途中まで）→「通信が途中で切れて、返事が途中で止まりました。『続けて』と送ると再開します。」
  - `safeguards flagged this session` →「このセッションは Claude の安全機能で止められました。`/model` で別のモデルにするか、新しいスレッドで始めてください。」
  - それ以外 →「『続けて』と送ると再開を試みます。」（前に付く「Claude Code が API エラーで止まりました。」を繰り返さない — #1180）
- あわせて `❌ Claude Code が API エラーで止まりました` の embed（同じ案内＋英語の最初の1文）が出る
- 英語の原文は、ミラーが**最初の1文だけ**を `-# ⚠️ API Error: …` の小さい1行にして出す。`Double press esc to edit your last message…` などペインの前に座っている人向けの手順は Discord に出さない
  - **同じターンの中で同じ1行は1回だけ**出す（#1251）。安全機能が要求のたびに拒否し、そのたびに作業が続くターンでは、
    同じエラーが何度も書かれる（本番では23秒で4回、同じ行が4通出ていた）。文が違うエラーは同じターンでも出し、
    次のターンではまた出す（ペインに直接打った指示で始まったターンも新しいターンとして数える — 中断されて `turn_duration` が無いときも。ターンの途中に届いた背景の処理の知らせや素の `<system-reminder>` の行は新しいターンではないので、数え直さない — #1285。Esc で止めたターン（`[Request interrupted by user…]` の行）のあとは、知らせや起床予定で始まったターンでも数え直す。API エラーで止まったターン（エラーの行のあとに道具の結果も返事も無いまま次の指示・知らせ・起床予定が来る — CLI が `turn_duration` を書かないことがある）のあとも同じで、次に来たものは新しいターンとして数え直す — #1294。エラーのあとに道具の結果が続いた（作業が続いた）ターンの途中の知らせは、#1285 どおりそのターンの中）。投稿に失敗した行は出したことにしないので、同じターンで次に同じエラーが来たときに出す。出さなかった分もログには INFO で `folded API error … (same line already posted this turn, not posted again)` と残る
- 利用上限（429）は別の扱い（上の「上限に当たったターン」、#631）。ターン終了イベントの `failure.reason` は `api_error`
- **Claude が自分から始めたターン**（背景の処理・サブエージェントの完了の知らせや起床予定で再開したターン — runner が走っていない）で
  止まったときも同じ扱いにする（#1131）。人のターンが API エラーで止まって `turn_duration` が書かれず、そのあと知らせや起床予定で Claude が始めたターンも、人のターンの続きではなく Claude が自分から始めたターンとして扱う（#1294。以前はこの ❌ も ⚠️ の1行も出なかった）。人のターンのエラーはそのターンのもので、知らせで始まったターンが何も書かずに終われば ❌ は出さない。c-lord が人のターンの止まったあと・知らせの前に再起動しても、読み返し（#1011）が同じ判定をするので同じになる。ミラーがそのターンの終わり（`turn_duration`）で、上と同じ1行
  `❌ Claude Code が API エラーで止まりました。<案内> @依頼者` を**1回**出す。呼ぶのはそのスレッドの直近の依頼者
  （c-lord が最後に走らせたターンを頼んだ人。webhook・bot・不明なら `DISCORD_OWNER_ID` へのフォールバック）。
  ターン終了イベントの出口（`CLORD_EVENT_LOG` / `CLORD_EVENT_WEBHOOK_URL`）を設定していなくても依頼者を呼ぶ（#1178。
  以前は出口が無いと依頼者を覚えず、owner を呼んでいた）。bot の再起動のあと、まだ誰も送っていないスレッドでも
  同じ人を呼ぶ: 記録してある直近のターンのきっかけのメッセージ（`sessions.trigger_message_id`）の送り主を読む
  （#1212。以前は再起動で依頼者を忘れ、人が次に送るまで owner を呼んでいた）。そのメッセージが webhook・bot・
  c-lord 自身の投稿、または読めない（10秒で読めない場合も）ときは owner へのフォールバック。スレッドの最初のターンのきっかけも記録する
  （以前は最初のターンでは記録の行がまだ無く、書かれていなかった）。
  `/skill` で始めたターンはきっかけのメッセージが無いので、記録を消す。再起動のあとは owner を呼ぶ
  （#1234。以前はその前にメッセージで依頼した人 — このターンを頼んでいない人 — を呼んでいた）。
  消すのは `/skill` の依頼が Claude のペインに届いた瞬間（送信 `send_input` や起動 `start_claude` が成功したとき —
  `RunConfig.on_prompt_sent`）で、送信に失敗した `/skill` は何も消さない。新旧は「記録した時刻」ではなく
  「ペインに届いた順」で決める — ペインは最後に届いた入力に答えるから。消す対象は、`/skill` を始めた時点で記録
  （メモリ・行・行待ち）にあったきっかけと、`/skill` の依頼より先にペインへ届いたメッセージのターンのきっかけ。
  ただし、まだペインへ向かっている途中のメッセージのターン（きっかけを記録したが、依頼をまだ送っていず、終わってもいない）の
  きっかけは消さない — その依頼は `/skill` のあとに届くので、答えるのはそのターン
  （#1262。以前は準備の間にペインへ届いて終わったメッセージのきっかけが残り、`/skill` の答えがその人への返信になり、
  再起動のあとその人を呼んでいた。逆に、`/skill` のあとに届くメッセージのきっかけを消して、その人への返信と呼び出しを失うこともあった）。
  メッセージのターンが、依頼をペインへ一度も届けないまま終わった（送信に失敗した等）ときは、そのターンは答えを持たないので、
  そのきっかけがまだ最新ならメモリと行から消す（#1262。以前は残り、ほかのターンの答えがその人への返信になり、再起動のあとその人を呼んでいた）。
  そのとき、それより前に依頼がペインへ届いたメッセージのターン（Claude がまだ答えている最中のこともある）があり、
  そのあと `/skill` が届いていなければ、消す代わりにそのターンのきっかけに戻す — ペインが答えているのはそのターンだから
  （#1270。以前は何も残らず、そのターンの答えが返信にならず、再起動のあとはその送り主ではなく owner を呼んでいた）。
  DB がロックされていて戻せなかったときは、WARNING を出して消す側に倒す。
  ただし、送信（`send_input` / `start_claude`）を始めたあとに取り消された（bot の停止など）ターンのきっかけは消さない — 送信がまだ途中で、
  実は届いていて再起動のあとに答えが来ることがあるため。送信を始める前に取り消されたターンは何も届けていないので消す（#1262）。
  送信が断られた（`send_input` / `start_claude` が失敗を返した — ペインには何も届いていない）あとに、理由を調べている間などに
  取り消されたターンも、何も届けていないので消す（#1271。以前は「送信を始めた」として残り、再起動のあと届いていない依頼の送り主を呼び、
  ペインが次に出す答えもその人への返信になっていた）。
  DB がロックされていて消す書き込みが断られたときは、そのスレッドの次の行の保存で消し、それまでは同じプロセスの中では
  記録に無いものとして扱う。bot を止めるとき（cog の unload）にも、再起動の知らせの記録（#870 のランプの書き戻し — 消すはずの
  きっかけは書き戻さない）のあとで消す（#1262）。既知の制限: 止めるときにも DB がロックされたままだったり、プロセスが
  unload を通らずに落ちたりすると、消すはずだったきっかけが残り、再起動のあとその人を呼ぶ。
  メッセージのターンがきっかけを記録する書き込みが DB のロックで断られたときも同じく、WARNING をログに出し、
  そのスレッドの次の行の保存で書き、それまでは同じプロセスの中ではそのきっかけを記録にあるものとして扱い、
  bot を止めるときにも書く（#1254。以前はログも出さずに捨て、行には前の依頼者のきっかけが残り、再起動のあと
  頼んでいないその人を呼んでいた）。書けないうちにそのきっかけが消された（`/skill` が後から届いた等）ときは、
  書いてから消したのと同じく記録は空になる（前の依頼者のきっかけには戻らない）。
  スレッドの最初のターンが記録の行を作る前に終わったときは、そのきっかけは捨てる
  （#1235。以前は次に行を作った別のターン — 別の人の `/skill` など — の記録として書かれていた）。
  embed は付かない（runner の結果を表す embed なので）。ターン終了イベントは `failure`（`api_error`）で、
  その知らせが背景のエージェント待ちで保留していた依頼のターンの終わりを解く場合も、その依頼のターンの `failure` として出す
  （以前は英語の1行だけが出て、イベントは `completion` だった）

判定は「**このターンが実際に始まったか**」で行います。具体的には、生成インジケータを一度も観測しておらず、かつペインから応答テキストが一度も取れていない場合を「開始していない」とみなします。ターンが**始まって**から静かになった場合（回答が transcript mirror 経由で届いたケース）は別で、これは正常終了です（#541）。

### 境界

- ターンの開始が遅れているだけの場合に「応答がありません」と言ってはいけない。開始までには**猶予**があり、その間はターンを終わらせない。猶予は Claude が起動済みかどうかに関わらず効く（かつては冷起動時にしか効かず、温かいセッションでは 60 秒静止しただけで終了扱いになっていた）
- ホストが混んでいると起動に時間がかかる。猶予はそれを見込んだ長さにする

### エラー時

- 通知の送信に失敗しても、ターンの処理を巻き添えにしない

## バグの例

- 何も返っていないのに `🟡 Claude has finished` が飛ぶ → **バグ**（#562）
- 回答が届いた**5分後**に 🟡 が飛ぶ → **バグ**（#583）。読み終えて次の作業に移った頃に呼ばれる
- **利用者が話しかけた数秒後**に「終わりました、返信が必要です」と飛ぶ → **バグ**（#583）。
  前のターンの終了処理が割り込みで初めて走っているだけで、完全に嘘
- ハングの疑い（⚠️）を出した直後に `🟡 Claude has finished` が並ぶ → **バグ**。2 つの判定が食い違っている（#473 で本文表記は削除され、⚠️ はリアクションのみになった）
- 応答があったターンで 🟡 が出ない → **バグ**
- c-lord の再起動をまたいだターンで、回答は届いたのに 🟡 と 📊 が出ない → **バグ**（#907）
- Claude が考え始める前（最初の1文字が出るまで）に 🟡 になる → **バグ**（#876）。
  この間ペインには時間表示の無い `✻ Simmering…` だけが入力欄の真上に出ていて、ほかに何も動かない。
  止めていた長い会話を開き直すと（キャッシュが冷えているので）これが 15 秒以上続き、
  画面のお知らせ行（週の使用量など）を「回答」と読んで 20 秒ほどでターンを閉じていた。
  入力欄の真上のステータス行に `…` が付いている間は、作業中として扱う
- Claude がバックグラウンドの調査を抱えたまま返事をしてターンを終えたのに 🟡 が来ず、次に一言送ると
  `⚡ Interrupted` になって調査が止まる → **バグ**（基準時刻を送信の 1 秒後に取っていたのは #916 で直した実例）
- 1 ターンで 🟡 が複数回飛ぶ → **バグ**
- ターンを頼んでいない人がメンションされる → **バグ**（#481 / #525）

## 根拠

- **#562** — 応答が無いまま「終わりました」と通知していた。yousan の直接報告:
  「僕が発言した時にいきなりメンションが飛んできて呼ばれることがある。でも全然実際の作業としては終わってないはずなのに」
- **#365** — 「新しいターンが実際に始まったか」のゲート。#562 はこのゲートを idle 経路が無視していたのが原因
- **#876** — 最初のトークンが出る前の、時間表示の無いスピナーを見落としていた（入力欄の下の行が多いと、下から 6 行の走査に入らない）
- **#541** — 正常終了したターンで誤ってタイムアウトを報告していた件。判定の順序はこの spec と同じ根（ポーリング脱出後の判定）にある
- **#481 / #520 / #525** — 誰をメンションするか
- **#495** — メンションを文末に置く理由
- **#473** — `⚠️ No activity for 30s` 本文は削除済み。ハングの疑いは ⚠️ リアクションだけで示す
- **#583** — 「回答を届けてもターンが閉じない」。出方は 2 つ（300 秒 backstop / 利用者の割り込み）で
  根は 1 つ。ターン終了判定を transcript のマーカーに移し、割り込みで終わったターンの呼び出しを止めた
