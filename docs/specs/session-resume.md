# あるべき動き: 止まったセッションを、メッセージ1通で復元できるか

> **#574 で改名**: 操作名は「終了」→「**停止**」、コマンドは `/close-workspace` → `/workspace-stop`、`/reopen-workspace` → `/workspace-start`、スレッド名のマーカーは `[終了]` → `[停止]` になりました。**旧コマンド名はエイリアスとして動き続けます**（利用者側の変更は不要）。既存スレッドに残る `[終了]` も引き続き正しく解釈されます。理由: 7日で自動発火するようになるため、何も失っていないのに「終了」と言われると誤解を招くから。詳細は [workspace-vocabulary.md](workspace-vocabulary.md)。

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

スレッドの tmux ウィンドウが消えたとき、c-lord は `/tmux-screenshot` や `/resync` で
**「このスレッドにメッセージを送れば自動で復元し、続きから再開します」** と案内することがあります。

この spec が決めるのは 2 つ、そして**その 2 つが必ず一致すること**です:

1. その案内を出してよいのはどんなときか
2. 案内どおりにメッセージを送ったとき、実際に何が起きるか

**案内する側と受け取る側が別々に条件を持つと、必ずズレます。** 実際 #538 では、案内は
「送れば復元します」と言い切る一方、受け取る側は `sessions` にレコードが無いスレッドの
メッセージを**返信もログも無しに捨てて**いました。利用者は案内どおりに送って無視され、
次に何をすればいいのか分からない状態に置かれました。だから両者は**同じ 1 つの判定**から
文言と受理条件を導きます（`c_lord/session_resume.py`）。

## 3 つの状態

スレッドは、利用者から見て次の 3 つのどれかです。

| スレッドの状態 | メッセージを送ると | 止まっているときの案内 |
|---|---|---|
| **動く**（記録があり、停止していない） | **実行される。** ペインが落ちていれば、これまでの会話ごと自動で復元してから実行（`--continue`, #270 / #464） | 「メッセージを送れば**自動で復元**し、続きから再開します」 |
| **停止**（`[停止]` / `/workspace-stop`, #512） | **止めた人による**（#700）。**自動停止（7日）なら 1 行だけ出て実行される**。**手動停止なら実行されない** —「▶️ 再開する」ボタン付きの案内が出る（押すと、いま送ったメッセージがそのまま走る） | 「メッセージを送ると**「▶️ 再開する」ボタンが出ます**」（手動停止のとき） |
| **記録が無い**（untracked） | **作業ディレクトリが残っていれば、1 行だけ出て再接続され、実行される**（#700）。**何も残っていなくても、リポジトリの紐付けがあれば同じスレッドで新しい会話として始まる**（#862）。**紐付けも無いときだけ実行されない** —「このスレッドには復元できるワークスペースがありません」＋次の一手が出る | 「前の会話は残っていません」「メッセージを送ると、**新しい会話として始めます**」 |

「記録が無い」は、30 日スイープ（#554）で**片付け済み**になった後・`/workspace-delete` した後・DB を
作り直した後・別ホストで作られたスレッドを見ている、などで起きます。

**片付け済み（#818）** は、30 日スイープが行を消さずに残した印です（`closed_at` = 片付けた日時、
`closed_reason = 'swept'`。新しい列・状態は足していない）。メッセージの扱いは「記録が無い」と同じで、
違うのは、何も残っておらず**リポジトリの紐付けも無い**ときの案内だけ —「🧹 このスレッドは YYYY-MM-DD に**片付け済み**です」
＋「いま送ったメッセージは Claude に届いていません」＋次の一手。行そのものが「c-lord のスレッドだった」
証拠になるので、人が立てたスレッドでも無音で捨てずに答えます。行は稼働中の一覧（`/clord-status`）・
ミラー起動・各種スイープからは外れ、`working_dir` / session id を後から引くためだけに残ります。**行が無くても
作業ディレクトリは残っていることが多く**（本番実測で 625 件中 313 件）、その場合は
c-lord 自身が繋ぎ直します。ディレクトリまで消えていても、紐付けがあれば作り直して新しく
始めます（#862）。

### 誰が止めたかで分ける（#700）

**c-lord が自動で止めたものは c-lord が自動で戻す。利用者が止めたものは利用者が戻す。**

| 止めたのは | 判定 | 投稿したとき |
|---|---|---|
| c-lord（7日 無操作の自動停止） | `closed_reason = "idle"` | 1 行出して**そのまま実行** |
| c-lord（30日 無操作の行スイープ） | 行が無く、作業ディレクトリが残っている | 1 行出して**再接続してから実行** |
| c-lord（30日スイープ ＋ ディレクトリの片付け） | 行も作業ディレクトリも無い。リポジトリの紐付けはある | 1 行出して**作り直し、新しい会話として実行**（#862） |
| 利用者（`/workspace-stop`） | `closed_reason = "manual"` / NULL | **実行しない**。「▶️ 再開する」ボタン |

なぜこの線か: 自動停止は**利用者が頼んでいない**。頼んでいない片付けの取り消しに承認を
求めるのは、c-lord の都合を利用者に払わせているだけです。逆に手動停止は決定なので、
[session-close.md](./session-close.md) の「自分で終わらせたなら、勝手に動き出さないでほしい」
を守ります。**倒す向きは常に「自動だと証明できたときだけ自動で戻す」。**

## あるべき動き（利用者から見て）

### 正常時

- **案内は、その時点で本当に起きることだけを言う。** 上の表の 3 行は、案内の文言と実際の
  動きが 1 対 1 で対応する。「復元します」と言われたなら復元されるし、復元できないなら
  そう言われる。
- **記録が無くても、繋ぎ直せるなら繋ぎ直して実行する（#700）。** 出るのは 1 行だけ:
  「🔗 しばらく使われていなかったため停止していました。再接続して続きから実行します。」
  会話の履歴（transcript）まで消えていたときは、そう言ったうえで**このスレッドの過去ログを
  作業ディレクトリに書き出して**引き継ぐ。⚠️ は付けない — 付けたら「届いていない」という
  嘘になる。
  - **書き出したことは Claude にも伝わる（#881）。** 再接続したあとの最初の依頼に「このスレッドの
    以前の会話は残っていません。これまでの Discord のやり取りを `.claude/clord-thread-history.md`
    に書き出してあります。経緯が必要なら読んでください（discord-read skill でも読めます。
    thread_id）」の 1 行が添えられる。#862 と同じく**読むかどうかは Claude に任せる**。
    到着時の自動再接続・webhook・`/clord`・手動の再接続（`/workspace-start` 等）のあとの
    次のメッセージ、どの経路でも同じ。「最初の」は**書き出した過去ログより新しい Claude の
    会話記録がまだ無い**ことで判定する（ディスクを見るので、手動の再接続と次のメッセージの
    間に bot が再起動しても一行は落ちない）。2 通目からは付かない。会話の履歴が残っていた
    再接続（続きから再開する方）には付かない
- **何も残っていなくても、リポジトリの紐付けがあれば同じスレッドで新しく始める（#862）。**
  1. 「🧹 前の会話は残っていないので、新しい会話として始めます」の 1 行が出る。
  2. 作業ディレクトリを作り直す（新しいスレッドを立てるときと同じ clone。スレッドの紐付けが
     あればそちら、無ければチャンネルの紐付け）。
  3. Claude Code を**新しい会話で**起動する。`--continue` / `--resume` で前の会話を開こうとしない
     （墓標に古い session id が残っていても使わない）。
  4. 送ったメッセージをそのまま実行する。最初の依頼にだけ「このスレッドの以前の会話は残って
     いません。必要なら discord-read skill でこのスレッドの過去のやり取りを読めます（thread_id）」
     の 1 行が添えられる。**読むかどうかは Claude に任せる**（自動で全部は読ませない）。
  5. 最初のターンで Claude が session id を出した時点で行が書かれる（墓標があればそれが
     「使用中」に戻る）。2 通目からは普通のスレッドと同じ。
  ⚠️ は付けない。`/clord <やること>` をスレッド内で打っても同じく新しく始まる。
- **リポジトリの紐付けも無いときだけ、メッセージは実行されない**（何を clone するか分からない）。
  そのときも黙って捨てられない。
  必ず次の 3 つが起きる:
  1. **ログに 1 行残る**（`thread=<id>` で grep できる）。「送ったのに何も起きない」を後から追える。
  2. **送ったメッセージに ⚠️ が付く。** 「見えてはいるが、実行していない」と一目で分かる。
  3. **スレッドに案内が出る**: 「このスレッドには復元できるワークスペースがありません」
     「いま送ったメッセージは Claude に届いていません」＋**次の一手**。
- **次の一手は具体的なコマンドで示す。** チャンネルで `/clord prompt:<やること>` か
  `/clord repo:<URL> prompt:<やること>`（新しいスレッドが立つ。前の会話は引き継がない）。

### 境界

- **同じスレッドに続けて送っても、長い案内文が毎回は出ない。** 案内は 1 スレッドにつき 1 回
  （bot の再起動でリセット）。ただし **⚠️ は毎回付く**ので、2 通目以降も「無視された」には
  ならない。
- **webhook から届いた普通の文も、人の投稿と同じく再接続（#700）・新しく始める（#862）の対象。**
  Claude どうしの発注（タスク管理スレッドが webhook の `?thread_id=` で古いスレッドに指示を流す）や
  OpenClaw の人格からの依頼が、片付け済みのスレッドで黙って捨てられないため（2026-10-08 yousan 指示）。
  ただし次の 2 つは会話を始めない:
  - **テキストコマンド**（`!close-workspace` など）はコマンドとして動く（`on_message` は扱わない）。
  - **c-lord 自身の決まった形の webhook**（`WebhookTriggerCog` のトリガー・`AutoUpgradeCog` の
    アップグレード）は、その Cog が `claims_message()` で自分のものと答えるので、そちらに任せる。
    利用者の Cog も同じ名前のメソッドを生やせば加われる（登録は不要）。
- **webhook には断りの返事をしない。ただし「捨てた」ことはログに残る。**
  紐付けが無い・c-lord の痕跡が無いなど、何も始められないときに、
  ⚠️ も案内文も出さない（監視・アラート系の webhook は返事を待っておらず、
  インシデント中に唯一読めるはずのスレッドを埋めないため — #556）。
  **黙るのは Discord 側だけで、ログには残す**: 同じスレッドについては**通常運用の
  ログレベル（INFO）で一定時間に 1 回**、`thread=<id>` 付きで出る（残りは DEBUG）。
  連投されてもログは溢れず、抑制した件数は次の 1 行が `(+N suppressed in the last Ms)` と
  して持つ（#678）。「Discord も無反応・ログも 1 行も無し」だと、送った側は
  「bot が落ちたのか / webhook が壊れたのか / スレッドが対象外なのか」を区別できない。
- **自分に関係ないチャンネルでは黙る。** 1 つのサーバーに複数の c-lord が居ることがあるため、
  案内を出すのは「このチャンネル（`DISCORD_CHANNEL_ID`）」か、`/clord-init` /
  `/clord-thread-init` でリポジトリが紐づいたチャンネルのスレッドだけ。それ以外では
  **ログだけ残して何も投稿しない**（全部の bot が同じ警告を並べない）。
- **立ち上がったばかりのスレッドには「記録がありません」と言わない。** `/clord` で作られた直後の
  スレッドは、Claude が最初のセッション ID を出すまで記録を持たない。その最中に追加のメッセージを
  送っても「復元できるセッションがありません」とは案内されない（記録はまさに今作られている最中で、
  そう言うのは事実に反する）。この窓では案内もリアクションも出さず、ログにだけ残す。
- **`/resync` などの「案内」は、いまも「記録がある」だけを『復元できる』と言う。** 記録を
  ディスクから作り直すのは別の判定（`plan_recovery`）で、案内の側がそれを先読みして
  「たぶんできます」と言うのは #538 と同じ嘘になる。**実際に届いたメッセージは**その別判定を
  使って繋ぎ直すので（#700）、案内が控えめな側に外れることはあっても、約束を破る側に外れる
  ことはない。
- **続ける会話が実際には無かったときも、1 通目はそのまま実行される。** 記録があっても
  `--continue` で戻せる会話がディスクに無いこと（そのスレッドで Claude が一度も走って
  いない、など）はある。そのときは**利用者が送り直さなくても**新規セッションとして起動し、
  **いま送った依頼をそのまま**実行する。1 通目が捨てられて「送り直したら動いた」には
  ならない（#657）。
- **起動の成否は「Claude がどうなったか」で判定する。時計では判定しない。** そのディレクトリで
  初めて Claude を起動するときはフォルダ信頼ダイアログ（trust prompt）が先に出る。
  ダイアログを表示している Claude は「まだ何も決まっていない」ので、**そこで成否を判定せず、
  ダイアログに答えたうえで「入力欄まで来た（成功）／終了した（失敗）」を待つ**（#657）。

### エラー時

- **案内やリアクションの投稿に失敗しても、他は止まらない。** どちらが落ちても**ログの 1 行は
  必ず残る**（そこだけは失敗しない順序で行う）。
- **記録を読めなかったとき**（DB エラー）は、案内は「復元できる」側の文言に倒す。記録がある
  スレッドは送れば実際に動くので、利用者を動く可能性の高い方へ送る。

## バグの例（こうなっていたらバグ）

- 「メッセージを送れば自動で復元します」と案内されて送ったのに、**返信もリアクションもログも
  出ない**（#538 そのもの）。
- 記録が無いスレッドに送ったのに、**ログに 1 行も出ない**（原因を追えない）。
- webhook で送ったメッセージが黙って捨てられ、**通常運用のログ（INFO）にも痕跡が無い**
  ため、後から `grep thread=<id>` しても 1 行も出ない（#678）。
- 逆に、連投してくる webhook 1 本で **INFO ログが同じ 1 行で埋まる**（#556 の懸念の再発）。
- **手動で停止した（`[停止]`）スレッドで「メッセージを送れば自動で復元します」と案内される**
  （実際に出るのは再開ボタン）。
- **自動停止（7日）や行スイープ（30日）のスレッドで、ボタンを押させられる**（#700 が直したもの）。
- **作業ディレクトリが残っているのに「復元できません」と言われる。**
- **片付け済みのスレッドで、リポジトリの紐付けがあるのに「届いていません」と断られる**（#862 が直したもの）。
- 新しく始めたはずなのに、**前の会話の続きとして返事が来る**（`--continue` / `--resume` している）。
- 新しく始めたスレッドで、**2 通目以降にも discord-read の一行が付く**。
- 「過去ログを引き継いで再接続します」と出たのに、**Claude への最初の依頼に過去ログの場所が
  書かれていない**（#881 が直したもの）。
- 片付け済みのスレッドに webhook で普通の文を送ったのに、**何も起きない**（#862 追加要件）。
- webhook の `!close-workspace` や CI トリガーの投稿で、**Claude の会話が始まる**。
- 記録が無いスレッドで、案内は出るのに**次に何をすればいいか書いていない**。
- 同じスレッドに 5 回送ったら、同じ長い案内が 5 回並ぶ。
- 復元対象のスレッドに送った **1 通目が ❌ で捨てられ**、同じ内容を送り直すと普通に動く（#657）。
- **案内の文言と、実際に受け付ける条件が別々の場所に書かれている**（また必ずズレる）。

## 根拠

- #270 / #464 — 落ちたペインの `--continue` 自動復元と、その告知。この spec の「動く」行。
- #464 ②-2 — 止まったセッションで `/tmux-screenshot` / `/resync` が行き止まりにならないよう
  復元導線を案内するようにした。ただし**復元できるかは確認していなかった**。
- #642 — #572 で「止まっている」が常態になり、案内文が `/tmux-screenshot` の通常の返答に
  なってしまったので、**復元できると分かっている verdict (`RESUMES`) では案内せず復元する**
  ようにした。案内と実際の受け付け条件を同じ `classify()` から引く形は変えていない。
- #512 — 「終了」を `closed_at` として記録。この spec の「終了」行（[session-close.md](./session-close.md)）。
- #522 — 1 サーバーに複数 c-lord が居るとき、関係ないチャンネルで喋らない。
- #538 — 案内と受理条件のズレを 1 つの判定に統合し、記録の無いスレッドを黙って捨てるのをやめた。
- #556 — その案内が webhook のアラートスレッドにも出てしまい、インシデント中のスレッドが
  ⚠️ と案内文で埋まった。webhook には返さない（Discord 側は黙る）ことにした。
- #678 — その「黙る」がログにも及んでいて（DEBUG のみ）、捨てたことが INFO に 1 行も
  残らなかった。うるささを戻さずに追跡性だけ回復するため、**スレッド単位・一定時間に
  1 回だけ INFO**（`c_lord/log_sampler.py`）にした。
- #657 — `--continue` の成否を**固定 3 秒後の生存確認**で決めていたため、trust prompt を
  表示中の Claude を「起動成功」と誤判定し、フレッシュ起動へのフォールバックが発動しなかった。
  1 通目が失われるのを止めるため、判定を「入力欄に到達したか／終了したか」に変えた。
- #700 — c-lord が自動で止めたワークスペース（7日停止・30日の行スイープ）に投稿したとき、
  ボタンを押させるのをやめて自動で戻すようにした。停止通知が既に
  「このスレッドに投稿しても再開できます」と約束していたのに、実装がそうなっていなかった —
  約束と実装のズレという意味で #538 と同じ形。**手動停止だけは従来どおりボタン。**
- #862（2026-10-08 追加）— webhook の普通の文でも再接続・新しく始めるようにした。#556 が
  黙らせたのは「断りの返事」であって、依頼そのものを捨てる理由ではなかった。
- #862 — 繋ぎ直すものが何も残っていない片付け済み・記録の無いスレッドでも、断らずに同じ
  スレッドで作業ディレクトリを作り直し、新しい会話として始めるようにした。会話ログ
  （Claude Code の `cleanupPeriodDays`、既定 30 日）も作業ディレクトリも消えているので
