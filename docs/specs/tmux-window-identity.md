# あるべき動き: 1 スレッド = 1 ウィンドウ（ターゲットの一意性）

> これは「あるべき動き」。理念 [`docs/PHILOSOPHY.md`](../PHILOSOPHY.md) の下位。迷ったら理念に照らす。

## これは何か

**同時に何本スレッドが立っても、1 スレッド = 1 ウィンドウで、そのウィンドウは必ずそのスレッドのチェックアウトに居ます。**
あるスレッド宛のキーストロークが、別のスレッドの作業ディレクトリに入ることはありません。

- 2本のスレッドを 1 秒差で立てても、両方そのまま起動する。片方が黙って死ぬことはない。
- スレッドのウィンドウ名（`w134`）は、そのセッションの中で重複しない。
- 万一（過去の残骸・手作業などで）同名ウィンドウが在っても、**そのせいで別スレッドの窓にキーが入ることはない**。

なぜ要るか: C-lord の核は「複数のセッションを開いたまま並行して進める」こと（[理念 A](../PHILOSOPHY.md#a-切れないどこからでも複数を並行して進められるこれが核)）。
**同時に立てられないなら「並行して進める」は成立しない。** さらに「A の指示が B のチェックアウトで実行される」は、
遅いとか不便とかではなく、**利用者が信頼して任せられなくなる**種類の壊れ方をする。

## ルールと根拠

### ウィンドウの指定は「名前」ではなく `window_id`

tmux は**ウィンドウ名の一意性を保証しない**。同名が2枚ある状態で `session:名前` をターゲットにすると、
tmux は**最初にマッチした方**を黙って選ぶ。`@thread_id` の読み書き・`send-keys`・`capture-pane` が
すべて名前ベースだったため、#649 では次が起きた:

```
@218 name=w134 @thread_id=1543882706067394591 path=.../1543882704230031461  ← 中身は別スレッド
@219 name=w134 @thread_id=(未設定)             path=.../1543882706067394591
```

thread `…706` のタグが `…704` の窓に書かれ、`…706` 自身の窓は最後まで無タグのままだった。

→ **内部の解決はすべて `window_id`（`@218` 形式）で行う。** `window_id` は tmux サーバが生きている限り不変で一意。
新規作成時に `new-window -P -F '#{window_id}'` で受け取り、以降そのIDだけをターゲットにする。
ウィンドウ**名**は「人間が `tmux attach -t <session>:<名前>` で開くための表示名」「スレッド名の `W<N>` ラベル」
としてのみ使う。

### 採番と直列化は「tmux セッション単位」

`resolve_tmux_manager()` は**スレッドごと / チャンネルごとに別の `TmuxSessionManager` インスタンス**を作る
（[CLAUDE.md の設計決定 10](../../CLAUDE.md)）。同じ repo に紐づくスレッドは同じ tmux セッションを指すが、
**インスタンスは別物**。したがって:

- **インスタンス変数のロックでは直列化にならない。** ロックは**セッション名をキーにしたプロセス内のロック**にする。
- **インスタンス変数のカウンタでは採番にならない。** 次の `w{N}` は毎回**live な tmux の状態**
  （`list-windows` の最大 `w{N}`）から決める。

この2つが揃って初めて「同時に2本立てても名前が衝突しない」が成り立つ。#374 の "Serialize the create-and-sort
critical section" は前者を意図していたが、守れていたのは同一インスタンス内だけだった。

### 実装の要点（`c_lord/tmux.py`）

| 項目 | 実装 |
|------|------|
| 直列化 | `_session_lock(session_name)` — モジュールレベルの `dict[str, threading.Lock]`。`TmuxSessionManager._lock` は毎回ここから引く（`session_name` を後から差し替えても正しいロックを取る） |
| 採番 | `_next_window_name()` が `list-windows` の最大 `w{N}` / `work{N}` から毎回決める。`_next_work_id` は `list-windows` 自体が失敗したときのフォールバックのみ |
| 二重作成の防止 | `create_session()` はロック**取得後にもう一度** `_find_window_for_thread()` で確認する（待っている間に別スレッドが作り終えている可能性がある） |
| 新規窓の同定 | `new-window -P -F '#{window_id}'` で ID を受け取る。以降 `@thread_id` 設定・resize・send・capture すべてこの ID をターゲットにする |
| マッピング | `_thread_to_window` は `thread_id -> window_id`。`_target()` が ID をそのまま使い、名前だけは `session:名前` に修飾する（`remap_window` など運用コマンド経由の名前入力用） |
| 重複の解決 | `_rebuild_mapping()` は `list-windows` 1発で `window_id` / 名前 / `@thread_id` / パスをまとめて読み、**`window_id` をキーに**クレームを集計する。ログも `@218 (w134)` 形式で出るので、別々の窓が同じ名前で出力されて自分自身と衝突しているように見えることはない |
| 永続マップ | `~/.cache/c-lord/<session>-window-map.json` は**名前**を保存する（tmux サーバ再起動で ID は振り直されるが、名前は tmux-resurrect が復元するため）。読み込み時に名前→`window_id` へ解決し、名前が曖昧なら**そのエントリを使わない**（推測しない） |

### 失敗したときの案内

同名ウィンドウが在ってターゲットを解決できないとき、**「ペインが落ちています。`/restart-claude` を」とは案内しない。**
ペインは生きているし、`/restart-claude` はウィンドウ**の中の** Claude を立て直すだけなので、名前の重複は残る
（#649 では、案内どおり操作しても直らないまま2スレッドが丸1日死んでいた）。
重複している名前と、ホストで実状態を見るコマンドを示す（`c_lord/claude/tmux_runner.py::_ambiguous_window`）。
文言の分岐そのものは [input-delivery.md](./input-delivery.md) を参照。

## バグの例

- 担当スレッドを2本続けて立てたら（1秒差）、同名の `w134` が2枚でき、片方の `@thread_id` がもう片方のスレッド ID になった。
  両スレッドとも Discord には「tmux のペインが入力を受け付けませんでした」が出て、`/restart-claude` しても直らず、
  4件の Issue が丸1日以上着手されないまま放置された（#649）
- `Duplicate @thread_id … claimed by w134, w134` というログが 42,001 行出続けた。名前でしか窓を呼べないので、
  ログの上では**別々の窓が自分自身と衝突しているように見えていた**（#649）

## 根拠

- #649 — 本ドキュメントの発端。根因は「同じ tmux セッションに `TmuxSessionManager` が複数できる」こと。
- #374 — window の並び順とクリティカルセクション。ロックの意図はここで入ったが、インスタンス変数だったため
  インスタンスをまたいで効かなかった。並び順そのものは [tmux-window-ordering.md](./tmux-window-ordering.md)。
- #427 — スレッド固有の repo 紐付け。これが「1つの channel に対しセッションが複数ありうる」＝
  「マネージャのインスタンスが複数ありうる」状況を常態化させた。
- #501 — 同じ `@thread_id` を複数の窓が主張したときの解決（Claude が動いている方を選ぶ）。
- 理念: 「複数を並行して進められる」は核。同時に立てられない・別スレッドに混入する、はその核を直接壊す。
